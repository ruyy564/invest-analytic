# Разработка агента: правила и проверенный опыт

Источник правил — статьи Anthropic («Building effective agents», «Writing effective tools for
agents», «Multi-agent research system», «Code execution with MCP», «Demystifying evals for AI
agents») плюс грабли этого репозитория. Перед изменением поведения агента прочитай чек-лист
и проверь, не нарушаешь ли пункт.

## 1. Главные ошибки, которые мы уже совершали

| Ошибка | Как выглядит | Правильно |
|---|---|---|
| Заготовка вместо ответа | промпт требует «бери строки брифинга как есть», пользователь получает пересказ | модель синтезирует: факт → механизм → сравнение → следствие → инвалидаторы |
| Шаблон вместо модели | код сам пишет «Причина не установлена» как основной ответ | шаблон — только страховка, когда модель промолчала или отказала |
| Отказ вместо похода за данными | «не могу предоставить список, откройте приложение» | при отказе — один повтор с инструкцией вызвать инструмент (`retryWithTools`) |
| Все инструменты сразу | 54 определения MCP в контексте, модель путается | отбор под вопрос (`tool-scope.ts`): база + расширения по теме |
| Хардкод компаний/фраз | списки тикеров, «омонимы» вместо поиска эмитента | инструмент (`invest_find_instrument`), данные в YAML, а не в коде |
| Отказ в экономических вопросах | «что такое ФРС» → «вне компетенции» | `ECONOMY_PATTERN` → экспертная ветка; знания из БЗ, данные из инструментов |
| Трактовка «нет данных» | «долг — нет данных» → «низкий долг» | строка «нет данных» — отсутствие факта, из неё нельзя выводить оценку |

## 2. Чек-лист перед изменением агента

- [ ] Вопрос относится к деньгам/экономике? Он не должен попадать в `off_topic`.
- [ ] Если не хватает данных — агент вызывает инструмент, а не отказывает.
- [ ] В промпте есть требование к аналитике (механизм, сравнение, сценарии), а не к пересказу.
- [ ] Набор инструментов для модели ограничен темой вопроса.
- [ ] Никаких захардкоженных названий компаний и готовых ответов в коде.
- [ ] Числа и вердикты кода берутся из данных; модель их не пересчитывает.
- [ ] Оценки помечены «(оценка)», рекомендаций «покупать/продавать» нет.
- [ ] Ошибки модели (пустой ответ, отказ, цензура) обрабатываются, а не показываются пользователю.
- [ ] Добавлены тест (unit) и кейс (`test/eval/cases`) на новое поведение.
- [ ] Прогнаны `npm test`, `npm run test:e2e`, `npm run eval`, `npm run lint`, живой прогон.

## 3. Инструменты (ACI)

- Описание инструмента пишется как docstring для нового сотрудника: что делает, когда звать,
  какие аргументы, чего ждать в ответ.
- Возвращай смысл, а не сырой JSON: фасады `instruments__*` + `summarizeFields`, компактные
  строки. Сырые ответы MCP режутся `clipToolResults`.
- Имена — `<server>__<tool>`; для сопоставления с локальными списками используй `baseToolName`.
- Не добавляй инструмент, если хватает фасада. Не передавай модели больше ~35 инструментов.
- Ошибка инструмента должна объяснять, что сделать: «нет данных по тикеру — проверь класс
  торгов», а не «error 400».

## 4. Промпты

- Один system-message: GigaChat не принимает второй (422).
- Не проси параллельные tool calls: GigaChat отклоняет несколько function results в одном
  сообщении — один вызов за круг.
- Формулируй цепочку рассуждения явно: событие → механизм → направление → сравнение →
  следствие → инвалидаторы.
- Ограничивай объём знаний в промпте (`knowledgeMaxChars`), иначе модель теряет факты.
- Запрещай конкретные ошибки словами: «не выводи оценку из "нет данных"», «не повторяй
  строку брифинга», «не подставляй тикеры из своих знаний».

## 5. Оценка качества (evals)

- Кейс = вопрос + окружение + ожидания (`answer`, `expectedTools`, `transcript`).
- Грейдеры: наличие/отсутствие фрагментов, числа, разделы, вызванные инструменты.
- `pass@k` — «хоть раз получилось», `pass^k` — стабильность; оба должны быть 100 % на `required`.
- Задачи брать из реальных провалов пользователей, а не придумывать.
- Читать транскрипты (`npm run replay -- <runId>`, `scripts/ask.mjs --save`), а не только счёт.
- Для многошаговых сценариев (review) проверять состояние (план, покрытие, отчёт), а не
  только текст ответа.

## 6. Специфика провайдера GigaChat

- Только один system message; второй — 422.
- Параллельные вызовы инструментов — 422, поэтому вызовы по одному за круг.
- Пустой ответ на уточняющий вопрос — норма: нужен повтор или ответ по фактам.
- Цензурные отказы («чувствительные темы») распознавать (`isRefusal`) и обходить:
  нейтрализовать брифинг, убрать политические сюжеты, затем факты.
- В JS `\w` не включает кириллицу: для русских паттернов `[а-яё]`, а не `\w`.

## 7. Как проверять изменения

```bash
npm run build && npm run lint
npm test                      # unit
npm run test:e2e              # граф, HTTP, MCP
npm run eval                  # pass@k / pass^k
node scripts/ask.mjs "вопрос" --full --approve   # живой прогон
```

Живой прогон обязателен для промптов и маршрутизации: тесты с fake-моделью не показывают
реакцию настоящей модели.

## 8. Что нельзя делать

- Отвечать пользователю текстом отказа провайдера или ошибкой инструмента.
- Возвращать сырой JSON брокера в ответ.
- Добавлять «если вопрос про X — ответить фразой Y» в код.
- Менять промпт без кейса в eval и без живой проверки.
- Расширять allowlist инструментов без необходимости.
