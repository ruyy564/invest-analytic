# OpenSpec Checkpoint

Фиксирует результат одного этапа OpenSpec коммитом и убирает временные файлы, которые
появляются от прогонов, сборки и тестов. Скилл ничего не меняет по существу: он только
проверяет, чистит и коммитит то, что уже сделано.

## Когда использовать

- после создания `proposal.md`, спеки-дельт, `design.md`, `tasks.md`;
- после завершения группы задач в `apply` (чекбоксы отмечены, тесты зелёные);
- после `archive`;
- по просьбе: «зафиксируй этап», «закоммить и почисти», «checkpoint».

Не использовать: посреди незавершённого этапа, при падающих проверках, во время
запущенного прогона сервиса (сначала остановить процесс, иначе логи пересоздадутся).

## Вход

- имя изменения — аргумент или контекст диалога (из `openspec list --json`);
- этап — аргумент (`--stage`) или определяется по изменённым файлам (см. таблицу).

Если изменение не определяется однозначно, показать список активных изменений и
спросить, к какому этапу относится работа.

## Этап 1. Очистка временных файлов

Сначала показать, потом удалить:

```bash
node scripts/clean-temp.mjs          # список того, что будет удалено
node scripts/clean-temp.mjs --yes    # удаление
```

Скрипт удаляет только закрытый список: `*.log`, `*.tmp`, `*.tsbuildinfo`, `health.json`,
`sid.txt`, `rid.txt`, `tool-dump.jsonl`, `report.md`, `coverage.json`, каталоги `tmp`,
`coverage`, `.nyc_output`, `.browser-profile`, `.langgraph_api`.

Никогда не удалять и не добавлять в коммит: `node_modules/`, `dist/`, `certs/`,
`data/state.sqlite*`, `.env`, `.env.local`, `openspec/specs/**` (кроме этапа archive,
где спеки меняются намеренно).

Если появляются временные файлы вне этого списка — не удалять их самовольно, а перечислить
и предложить расширить `scripts/clean-temp.mjs` отдельной правкой.

## Этап 2. Проверка этапа

| Этап | Что проверить |
|---|---|
| proposal / specs / design / tasks | `openspec validate <change>` |
| apply (группа задач) | `npm run build`, `npm run lint`, `npm test`; при изменениях поведения графа, API, источников или отчёта — ещё `npm run test:e2e` |
| archive | `openspec validate <change>` и `openspec list` (активных изменений не осталось) |

Правила:

- проверка упала — остановиться, показать вывод, ничего не коммитить;
- проверки не относятся к этапу (например, правка только документации) — не запускать
  долгие тесты «на всякий случай», достаточно валидации OpenSpec;
- таймауты или внешние сбои (сеть, 403 от лент) не считать провалом, если тесты прошли.

## Этап 3. Что попадёт в коммит

```bash
git status --porcelain
git diff --stat
```

- Пустой статус — сообщить «коммитить нечего» и завершить без пустого коммита.
- Сначала показать список файлов, затем добавлять. `git add -A` допустим только когда все
  изменения относятся к текущему этапу; иначе добавлять конкретные пути.
- Файлы вне этапа (чужая правка, эксперимент, локальный конфиг) — не коммитить,
  перечислить отдельно и спросить.

Проверка на секреты перед коммитом:

```bash
git diff --cached | Select-String -Pattern "(api[_-]?key|secret|password|token|credential)\s*="
```

Найденное совпадение — остановиться и разобраться: ключи в репозиторий не попадают.

## Этап 4. Коммит по этапу

| Этап | Шаблон сообщения |
|---|---|
| proposal | `docs(openspec): предложение <change>` |
| specs | `docs(openspec): спеки <change>` |
| design | `docs(openspec): дизайн <change>` |
| tasks | `docs(openspec): задачи <change>` |
| apply | `<type>(<scope>): <что сделано>` |
| archive | `docs(openspec): архивировать <change>` |

`type` для apply — `feat`, `fix`, `refactor`, `test`, `docs` по содержанию работы;
`scope` — модуль (`agent`, `report`, `knowledge`, `news`, `config`…). Пример:

```bash
git add <paths>
git commit -m "feat(knowledge): каталог тем вместо одного файла" -m "Что изменилось и зачем одной-двумя фразами. Какие проверки прошли: build, lint, unit. Что осталось на следующий этап."
```

Тело коммита: что сделано, зачем, какие проверки прошли, что сознательно не вошло.
Коммит — один на этап: не смешивать в нём артефакты OpenSpec и код следующего этапа.

## Этап 5. Отчёт

Показать коротко:

- этап и изменение;
- что удалено при очистке (файлы и объём);
- что вошло в коммит (хеш, число файлов, префикс сообщения);
- какие проверки прошли;
- какой этап следующий по `openspec instructions apply --change <change> --json`.

## Guardrails

- Не менять содержимое этапа: скилл фиксирует, а не исправляет. Найденная ошибка — повод
  остановиться и сообщить, а не «поправить по пути».
- Не коммитить при падающих проверках и незакрытых задачах этапа.
- Не выполнять `git commit --amend`, `git push --force`, `git reset --hard`, `git clean -fdx`
  без явной просьбы пользователя.
- Не пушить: если нужен push, это отдельная просьба.
- Не удалять временные файлы вне списка `scripts/clean-temp.mjs` и не трогать данные
  прогонов (`data/state.sqlite*`) — это состояние, а не мусор.
- Не создавать пустой коммит и не «докидывать» мелочи в предыдущий.
- Сообщать о конфликте: если в рабочем дереве есть изменения другого этапа, этап считается
  незавершённым.

## Чек-лист перед завершением

- [ ] временные файлы удалены (`node scripts/clean-temp.mjs` показывает «Временных файлов нет»);
- [ ] проверки этапа прошли;
- [ ] в коммит не попали `.env`, состояние, сертификаты, `dist`, `node_modules`;
- [ ] сообщение соответствует этапу и содержит причину изменения;
- [ ] в отчёте назван следующий шаг OpenSpec.
