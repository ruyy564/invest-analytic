# Design

## Context

Смотри `proposal.md` — Why. Технические ограничения, которые формируют подход:

- Текущий граф: 11 нод (`classify`, `offTopic`, `help`, `knowledge`, `news`, `agent`,
  `approve`, `tools`, `plan`, `collect`, `report`) и две топологии в одной функции
  (`reviewEnabled`), собранные вручную.
- Модель GigaChat: нестабильный function calling и SSE, отказы в текстовых
  разделах, поэтому часть решений ранее ушла в детерминированные правила.
- Каталог инструментов: 55 MCP-инструментов в allowlist + 6 локальных + 4
  алиаса ≈ 65 инструментов, привязанных к модели.
- Логика релевантности новостей распределена по 8 файлам, парсинг — внутри
  адаптеров, база знаний смешивает роли «контекст промпта», «ответ» и «роутинг».
- Уже есть и сохраняется: чекпоинтер (SQLite/Memory), подтверждение через
  `interrupt`/`Command`, бюджеты вызовов, LangSmith-трассировка, 336 unit и 28
  e2e тестов.

## Goals / Non-Goals

**Goals:**

- Сделать поведение измеримым (evals) и наблюдаемым (`runId`, журнал прогона).
- Свести топологию к шести нодам и одному подграфу, чтобы одна правка не
  задевала несвязанные сценарии.
- Сократить каталог инструментов до восьми доменных фасадов.
- Свести правила релевантности источников в одну версионируемую политику.
- Задать структуру папок, в которой новая возможность, нода, инструмент,
  источник или секция добавляются по чек-листу.
- Дать поток событий и отмену, не ломая текущий HTTP-контракт.

**Non-Goals:**

- Замена GigaChat на другую модель и настройка провайдеров.
- RAG по большому корпусу знаний (остаётся каталог тем).
- Мультиагентные системы и параллельные «исследователи».
- Отказ от детерминированного отчёта: числа по-прежнему считает код.
- Переписывание парсеров брокера, которые уже отдают стабильный JSON.
- Полное удаление legacy-топологии в этом же изменении.

## Decisions

### D1. Шесть нод верхнего уровня плюс подграф `review`

`guard → router → (respond | agent ⇄ tools | review) → respond`.

Нода оправдана, если принимает решение, видна отдельным спаном и может быть
выключена независимо. Под это не подпадают `news`, `help`, `knowledge`,
`offTopic`: они становятся путём ответа, тулом или ресурсом.

- Альтернатива «оставить 11 нод»: каждая новая формулировка требует правки
  ветки; отладка идёт по 11 файлам.
- Альтернатива «чистый ReAct, 3 ноды»: детерминированный разбор портфеля
  перестаёт быть воспроизводимым, а отчёт — проверяемым.
- Альтернатива «15 нод на каждый сценарий»: дублирование рендера и проверок.

### D2. Восемь доменных фасадов вместо 65 инструментов

Модель видит `portfolio__snapshot`, `instruments__find`, `instruments__prices`,
`instruments__candles`, `instruments__forecast`, `instruments__dividends`,
`instruments__meta`, `news__search`. Внутри — MCP-вызовы и конвейер источников.

- Альтернатива «оставить каталог»: точность выбора падает, уже сейчас
  компенсируется костылями (`snapshotCall`, `PORTFOLIO_INTENT`).
- Альтернатива «динамическая загрузка тулов по сценарию»: модель всё равно
  выбирает из большого набора, а отладка усложняется из-за разных каталогов.
- Альтернатива «один тул-исполнитель кода»: сильнее зависит от качества
  генерации кода у провайдера, неприемлемо для GigaChat.

### D3. Планировщик по схеме с детерминированным фолбэком

Модель возвращает план (`шаги: [{tool, args}]`) по строгой схеме; код
валидирует и исполняет. При двух невалидных ответах или недоступности модели
применяется план сценария.

- Альтернатива «свободный ReAct»: у провайдера нестабильный tool calling,
  прогон уходит в цикл и требует подтверждения повторно.
- Альтернатива «только код-план»: сохраняется текущая проблема «новый вопрос —
  правка кода».
- Метрика `fallbackRate` — условие обратимости решения (см. риски).

### D4. Типизированный результат узла

Результат узла — структурированный объект (`kind: facts | analysis | report`,
`payload`, `coverage`, `partial`, `stopReason`). Строковые маркеры
(`REPORT_MARKERS`, `hasBudgetError` по тексту) удаляются.

- Альтернатива «оставить строки»: контракт не типизируется, любая правка
  формулировки ломает поведение незаметно.

### D5. Конвейер источников со стадиями и политикой в данных

`source → extract → normalize → policy → dedupe → rank → select → present`.
Политика — `data/policy/news.yaml` с версией. Каждая стадия возвращает
`StageReport` (получено/сохранено/отброшено с причинами).

- Альтернатива «починить фильтры в каждом адаптере»: восемь точек правды
  сохраняются, диагностика остаётся невозможной.
- Альтернатива «LLM-фильтрация всего потока»: дорого, недетерминированно и не
  даёт объяснимого решения.

### D6. База знаний — ресурс и путь ответа, не инструмент

Справочный контент подставляется приложением (контекст промпта) или отдаётся
детерминированным путём (`router → respond`). Тул не создаётся.

- Альтернатива «тул `knowledge__search`»: поиск не нужен для 17 тем, а решение
  модели там, где нет выбора, добавляет нестабильность.
- Переход на RAG оставляет возможность добавить тул позже — это не ломает
  текущий контракт.

### D7. Структура `platform / shared / capabilities / transports`

Домен внутри возможности (`domain / services / adapters / tools / present`),
`agent` — только оркестрация. Границы проверяются архитектурным тестом
(`test/unit/architecture.spec.ts`), читающим импорты.

- Альтернатива «eslint-plugin-boundaries»: дополнительная зависимость и
  настройка под flat config; архитектурный тест проще и даёт понятные сообщения.
- Альтернатива «оставить плоский `src`»: продолжается смешение осей (домен,
  транспорт, роль в графе).

### D8. Логи: pino JSON + собственный `runId` + журнал прогона

`runId` генерируется до запуска графа, кладётся в `config.metadata` и в
child-logger. Журнал прогона — отдельная запись (шаги, инструменты, покрытие,
стоимость), пригодная для воспроизведения. Формат — JSONL, по файлу на прогон в
каталоге `STATE_RUNS_DIR` (по умолчанию `.state/runs`); SQLite не смешивается с
чекпоинтами, чтобы очистка сессий не удаляла историю прогонов.

- Альтернатива «Nest Logger + парсинг»: неструктурно, нет корреляции.
- Альтернатива «только LangSmith»: внешняя зависимость и недоступность офлайн;
  локальная отладка требует сети.
- Альтернатива «сразу OpenTelemetry SDK»: избыточно до появления второго
  потребителя; имена полей делаем совместимыми (`gen_ai.*`), чтобы перейти.

### D9. Свой раннер evals на JSON-кейсах

Кейсы — файлы; раннер — скрипт с режимами `offline | live | judge`; грейдеры —
код и LLM-судья с версией рубрики.

- Альтернатива «LangSmith datasets/evals»: требует сети и ключа в CI, сложнее
  для офлайн-регрессий.
- Альтернатива «только jest»: не выражает trials, метрики и LLM-грейдеры.

### D10. SSE через `graph.streamEvents`, именованные события

`event: run_started | intent | approval | tool_call | tool_result | delta |
completed | failed | cancelled`, `data: {runId, ...}`.

- Альтернатива «polling статуса»: лишние запросы и задержка.
- Альтернатива «WebSocket»: двусторонний канал не нужен, отмена — отдельный
  запрос по `runId`.

### D11. Guardrails: `guard` до модели и детектор отказа в `respond`

Посторонние темы и торговые действия отсекаются детерминированно; отказ модели
распознаётся в `respond` и заменяется фактами; инъекции внутри данных не влияют
на политику, потому что политика живёт вне модели.

- Альтернатива «только промпт»: не гарантирует отказ, уже наблюдались отказы и
  ложные классификации.
- Альтернатива «внешний модератор»: дополнительная задержка и стоимость.

### D12. Миграция флагами, re-export, без «большого взрыва»

`AGENT_MODE=legacy|agent`, `NEWS_POLICY_V2`, `SSE_ENABLED`. Старые модули
остаются re-export'ами до завершения переноса.

## Risks / Trade-offs

- **GigaChat не тянет планировщик (fallbackRate > 30%)** → метрика в evals;
  если порог превышен, остаёмся на декларативных скиллах без агентской петли.
- **Двойная поддержка двух режимов затягивается** → срок жизни legacy не более
  двух релизов, затем удаление; иначе код снова станет «свалкой».
- **pino ломает привычный формат ошибок Nest** → отдельный logger-модуль и тест
  формата записи; исключения не логируются дважды.
- **LLM-судья нестабилен** → калибровка на 20–30 кейсах против человека,
  фиксированная рубрика и температура 0; в CI по умолчанию только код-грейдеры.
- **Политика в YAML превращается в «код в данных»** → правила ограничены
  регулярками и списками; сложная логика остаётся в чистых функциях.
- **Отмена удаляет состояние прогона** → отмена идемпотентна и не удаляет
  чекпоинт; удаление — только по TTL.
- **Рефакторинг папок конфликтует с параллельными изменениями** → перенос по
  одной возможности, re-export, зелёные тесты на каждом шаге.
- **Стоимость live-evals** → офлайн в CI, живой режим по расписанию и на релиз.

## Migration Plan

1. **M0 — измерение и наблюдаемость** (поведение не меняется): журнал прогона,
   `runId`, pino, архитектурный тест-заготовка, eval-раннер с текущими кейсами.
2. **M1 — политика источников**: `data/policy/news.yaml`, `CanonicalItem`,
   `StageReport`, golden-тесты; флаг `NEWS_POLICY_V2`, сравнение на evals.
3. **M2 — структура**: `platform/`, `shared/`, `capabilities/news`,
   `capabilities/knowledge`, `transports/`; старые пути — re-export; включение
   архитектурного теста.
4. **M3 — каталог фасадов и планировщик**: 8 тулов с алиасами старых имён,
   `router` + `guard`, `AGENT_MODE=agent` для одного сценария (бумага), сравнение
   на evals.
5. **M4 — контракт и подграф**: типизированный результат узлов, подграф
   `review`, `respond` с guardrails; удаление строковых эвристик.
6. **M5 — поток и отмена**: SSE-события, отмена по `runId`.
7. **M6 — удаление legacy**: старые ноды, алиасы и флаги; обновление
   документации и `docs/structure.md`.

Откат на каждом шаге — флаг в `false` и re-export; данные и чекпоинты
совместимы, миграция схемы не требуется.

## Open Questions

- Порог `fallbackRate` для окончательного отказа от агентской петли: 30% или
  ниже (решение по данным первых двух релизов).
- Нужен ли LLM-судья в nightly-режиме или достаточно ручного прогона на релиз.
