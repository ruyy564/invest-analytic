# Design

## Context

См. `proposal.md` — Why. Что важно из текущего состояния:

- Вопрос про возможности сейчас распознаётся внутри ноды ответа
  (`CAPABILITIES_PATTERN` в `src/agent/prompts/off-topic.ts`,
  проверка в `src/agent/nodes/agent.node.ts`). До этой проверки вопрос проходит
  `classify`, и модель может отнести его к `off_topic` — тогда пользователь
  получает отказ раньше, чем справку.
- Текст справки — один строковый литерал рядом с отказами (`OFF_TOPIC_ANSWER`,
  `NO_TOOLS_ANSWER`), поэтому он устаревает вместе с возможностями и не покрыт
  проверками содержания.
- В графе уже есть две терминальные ноды без данных: `offTopic` и `news`
  (после изменения `market-news-feed`). Это готовый образец для справки.

## Goals / Non-Goals

**Goals:**

- Один предсказуемый ответ на любой вопрос про возможности: без данных, без
  подтверждения, без модели.
- Единая карта возможностей, из которой собирается текст: правка в одном месте,
  тесты проверяют содержание.
- Справка не обещает отключённого: состав зависит от `REVIEW_ENABLED` и
  `NEWS_FEED_ENABLED`.

**Non-Goals:**

- Интерактивное меню/кнопки и «онбординг» с диалогом.
- Генерация справки моделью или из документации во время работы.
- Локализация (только русский).
- Обучение пользователя на примерах данных портфеля (справка не читает данные).

## Decisions

### 1. Отдельная терминальная нода `help`, а не проверка внутри `agent`

Проверка внутри ноды ответа стоит *после* классификации: если модель решила, что
«что ты умеешь» — посторонняя тема, до неё дело не доходит. Нода `help`
включается маршрутом из `classify`, поэтому порядок перестаёт иметь значение, а
справка не зависит от доступности модели и её таймаутов.

Альтернатива — оставить как есть и поправить только классификатор: дешевле, но
справка продолжит жить в ноде, которая «умеет всё», и её поведение будет
зависеть от того, дойдёт ли прогон до этой ноды.

### 2. Интент `agent_help` определяется правилом до модели

Список формулировок («что ты умеешь», «чем можешь помочь», «что здесь можно
узнать», «кто ты», «твои возможности») проверяется в `classify` до вызова модели,
как это уже сделано для отказов и новостей. Модель используется только если
правило не сработало.

Альтернатива — отдать распознавание модели: именно она сейчас и относит справку
к посторонним темам, поэтому правило надёжнее.

### 3. Текст собирается из карты возможностей, а не пишется строкой

Вводится структурированный список: `id`, заголовок, описание, примеры вопросов,
флаг «требует ли включённой возможности» (`review`, `news`). Из него строится
markdown-ответ. Это даёт три свойства: правка в одном месте, тест «каждой
возможности есть пример», тест «включённость учитывается».

Альтернатива — один многострочный литерал (как сейчас): любое изменение текста
не проверяемо, а устаревание заметно только пользователю.

### 4. Отключённые возможности помечаются, а не обещаются

Если `REVIEW_ENABLED=false`, раздел разбора не показывается; если
`NEWS_FEED_ENABLED=false`, раздел новостей помечается как отключённый. Так
справка не расходится с фактическим поведением.

### 5. Приоритет правил в классификаторе

Порядок: справка → новости → разбор → отказ. Справка идёт первой, потому что её
формулировки («что ты умеешь») не должны перехватываться ничем другим. Вопросы с
тикером или портфелем по-прежнему уходят в свои ветки: справка распознаётся
только на «пустых» формулировках про сам сервис.

### 6. Место текста — отдельный модуль

`src/agent/prompts/capabilities.ts`: карта возможностей, сборка ответа и
регулярка распознавания. Из `off-topic.ts` текст удаляется — там остаются только
отказы, у которых другая задача.

### 7. Ответ API

`intent: "agent_help"`, `status: "completed"`, без блока `report` и без
`partial`. Новых полей не добавляем: клиенту достаточно `intent` и `answer`.

## Risks / Trade-offs

- [Справка разойдётся с реальностью] → карта возможностей в одном файле и тест,
  который проверяет наличие раздела для каждой ветки; при добавлении ветки
  задача обновления справки попадает в чеклист изменения.
- [Правило перехватит лишний вопрос] → список формулировок узкий (про сам
  сервис), а вопросы с тикером, счётом и портфелем исключаются проверкой области.
- [Справка станет длинной] → разделы короткие: одна строка описания и один-два
  примера на возможность.

## Migration Plan

1. Добавить ноду и правило, оставив прежнюю проверку в `agent` как страховку на
   один релиз.
2. Удалить старую проверку и текст из `off-topic.ts` после зелёных тестов.
3. Откат не требует миграций: при отключении ноды (`AGENT_HELP_ENABLED=false`)
   вопрос уходит прежним маршрутом `data_lookup`.

## Open Questions

Нет: спорные места (нода вместо проверки в `agent`, правило вместо модели,
карта вместо литерала, учёт флагов) зафиксированы выше.
