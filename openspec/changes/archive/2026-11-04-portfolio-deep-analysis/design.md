# Design

## Context

Мотивация — в `proposal.md`. Существующее устройство, которое определяет подход:

- Граф `classify → (offTopic | agent ⇄ approve → tools)`; `approve` ставит `interrupt` по `tool_calls` последнего сообщения, `tools` — стандартный `ToolNode`. Роутер в `routers.ts` спрашивает `ApprovalPolicyService.requiresApproval` по имени инструмента.
- Реестр MCP уже собирает **локальные агрегаторы** рядом с инструментами сервера: `portfolio_all_accounts` (обход всех счетов, сводка кодом) и `price_dynamics` (свечи → цифры кодом). Это единственный проверенный способ заставить GigaChat не «вспоминать» числа.
- Отчёт по портфелю формируется детерминированно (`src/agent/report/portfolio-report.ts`), а узел агента перехватывает готовый отчёт по маркерам и отдаёт его без генерации, потому что пересказ большого отчёта упирается в таймаут 15 с.
- Бюджет прогона и таймауты зашиты константами: 8 вызовов / 30 с, вызов инструмента 8 с, дедлайн прогона 30 с, шагов графа 12.
- Подтверждение запрашивается на каждый набор `tool_calls`, поэтому цикл «прочитать счета → прочитать портфель → прочитать позиции» даёт несколько подтверждений подряд.
- LLM привязывается ко всему набору инструментов сразу (`bindToolsCompat`), а у GigaChat и OpenAI-совместимых провайдеров есть практические пределы на число функций в запросе.

## Схема

### Граф прогона

```
POST /api/v1/agent/chat
        │
        ▼
   ┌──────────┐
   │ classify │  router-model → метка + вид ответа
   └────┬─────┘
        │
        ├── off_topic ──────────────────────────────► offTopic ─► END
        │
        ├── data_lookup / security_analysis ────────► answer ⇄ approve ─► tools ─┐
        │                                                  └──────────────────────┴─► END
        │
        └── portfolio_review ─► plan ─► approve ─► collect ─► report ─► END
```

Лёгкая ветка не изменилась: модель сама вызывает инструменты, `approve` подтверждает
набор `tool_calls` по правилам. Ветка разбора включается только для `portfolio_review`.

### Ветка разбора портфеля

```
plan
 ├─ читает шаблон отчёта (reports/portfolio-review.yaml)
 ├─ выводит из шаблона список нужных поставщиков фактов
 ├─ служебно узнаёт открытые счета (инструмент без подтверждения)
 └─ пишет state.plan = [ { tool, args, group, priority } … ]
        │
        ▼
approve ── interrupt ─► 202 { approval: { question, actions, plan: { kinds, requests, accounts } } }
        │
        ▼ (approved)
collect
 ├─ пачки по RUN_PARALLELISM, обязательные источники первыми
 ├─ дедупликация по tool + стабильный args
 ├─ общий бюджет: RUN_TOOL_MAX_CALLS / RUN_DEADLINE_MS
 └─ coverage = { ok: [...], missing: [ { source, reason } ] }
        │
        ▼
report
 ├─ providers × N → факты (структура, концентрация, динамика, аналитика, новости, налоги, пробелы)
 ├─ рендер: markdown + структурированный JSON + templateVersion
 ├─ интерпретация: ОДИН вызов LLM по facts.brief → «макро и цикл», «итог и совет»
 └─ сохранение отчёта: reportId + coverage
        │
        ▼
       END ─► 200 { answer, report: { reportId, type, asOf, coverage }, partial }
```

### Слои и владельцы данных

```
api/agent.controller, api/reports.controller
        │
        ▼
agent/graph/build-graph.ts + routers.ts
        │            │
        │            ├─► agent/nodes/      classify · plan · approve · collect · report · agent · offTopic
        │            ├─► agent/collection/ planner · executor · coverage · providers/*
        │            └─► agent/report/     template-loader · engine · renderers · prompts/*
        ▼
tools/tools.module.ts ─ тематические инструменты
        ├─ portfolio__snapshot · portfolio__review
        ├─ security__brief
        ├─ market__price_dynamics · market__news_digest · market__tax_watch
        └─ macro__key_rate
                │
                ▼
tools/sources/ ─ реестр источников
        ├─ tinkoff  (MCP → McpProxyService → Tinkoff MCP, read-only)
        └─ cbr      (сид-файл или live → кэш в SQLite)
                │
                ▼
        state/ SQLite: чекпоинты сессий + сохранённые отчёты (reportId, templateVersion, TTL) + кэш источников
```

### Состояние прогона

| Поле | Кто пишет | Зачем |
|---|---|---|
| `messages` | все узлы | история прогона и чекпоинт |
| `intent` | `classify` | выбор ветки и вид ответа |
| `plan` | `plan` | перечень чтений для подтверждения и сбора |
| `coverage` | `collect` | что получено, что недоступно и почему |
| `reportId` | `report` | выгрузка отчёта по идентификатору |
| `partial` | `collect`, `report` | пометка неполного результата |
| `dataAsOf` | `collect` | время данных в ответе |
| `approvalRequestedAt` | `approve` | проверка срока подтверждения |

### Бюджеты и таймауты

| Что | Лёгкая ветка | Ветка разбора | Откуда |
|---|---|---|---|
| Вызовы инструментов | 6–8 | 40 | `RUN_TOOL_MAX_CALLS` |
| Дедлайн прогона | 30 с | 90 с | `RUN_DEADLINE_MS` |
| Таймаут вызова | 15 с | 15 с | `MCP_TOOL_TIMEOUT_MS` |
| Параллельность | 1 | 4 | `RUN_PARALLELISM` |
| Бумаг с аналитикой | — | 15 | `REVIEW_MAX_INSTRUMENTS` |
| Вызовов LLM | 1–3 | 2 (классификация + интерпретация) | — |
| Подтверждений | по правилам | 1 на прогон | `approval-policy` |


## Goals / Non-Goals

**Goals:**

- Один вопрос — один подтверждённый план чтений — один отчёт; сбор данных не зависит от того, что «вспомнит» модель.
- Все read-only данные брокера доступны агенту, при этом привязка инструментов к модели остаётся компактной.
- Числа в отчёте считает код; модель отвечает только за интерпретацию, помеченную как оценка.
- Лимиты, глубина и стоимость прогона управляются конфигурацией, а не правкой кода.
- Существующие сценарии (сводка по счетам, динамика цены, дисклеймер, частичный ответ) продолжают работать.

**Non-Goals:**

- Торговые и денежные операции, заявки, стоп-заявки — остаются запрещёнными.
- Внешние источники макро и аналитики в этой итерации не подключаются (только задел через `MCP_SERVERS`).
- Асинхронные задания, стриминг ответа и UI — вне рамок.
- Персональный риск-профиль пользователя и пороги «под клиента» — фиксированные пороги на эту итерацию.

## Decisions

### D1. План сбора вместо свободного цикла модели

`classify` даёт метку. Для `portfolio_review` роутер уводит прогон в отдельную ветку `plan → approve → collect → report`; для `data_lookup` и `security_analysis` остаётся прежний путь через узел ответа. Узел `plan` строит план: список записей `{ tool, args, priority, group }`, где `group` — вид данных (счета, портфель, цены, дивиденды, фундаментал, прогнозы, новости, индексы, сигналы, операции). Узел `collect` исполняет план пачками, узел `report` собирает отчёт по шаблону.

Альтернативы:

- *Оставить свободный цикл, подняв бюджет до 40 вызовов.* Модель пропускает источники, повторяет вызовы, а на GigaChat уходит в лишние круги подтверждения. Отклонено.
- *Полностью детерминированный отчёт без модели вообще.* Даёт честные числа, но не даёт интерпретации (цикл, секторы, совет), которую просит пользователь. Отклонено как единственный вариант.

Выбран гибрид: обязательная часть плана исполняется кодом, добор — моделью в рамках остатка бюджета. Это сохраняет текущий цикл `answer ⇄ tools` как «второй шанс», но перестаёт быть основным механизмом.

### D2. План строится узлом и подтверждается тем же `approve`

Узел `plan` кладёт план в состояние и передаёт управление в `approve`. Узел `approve` становится общим для двух источников решения: для лёгкой ветки — `tool_calls` последнего сообщения модели, для ветки разбора — `state.plan`. Payload в обоих случаях содержит вопрос, перечень планируемых чтений, их число и затронутые счета.

Альтернатива — отдельный `interrupt` внутри `collect`: дублирует механику `approve`, ломает возобновление прогона из чекпоинта и правила подтверждений. Отклонено.

Список счетов к моменту запроса подтверждения уже известен: `invest_list_accounts` помечен как служебное чтение без подтверждения.

### D3. Агрегаторы остаются только для точечных карточек

Правило: агрегатор нужен там, где данные разных бумаг или счетов сводятся в один ответ для лёгкой ветки. Сохраняются `portfolio_all_accounts` (сводка по счетам) и `price_dynamics` (динамика цены), добавляется `security_brief` (карточка бумаги: цена, динамика за периоды, дивиденды, фундаментал, консенсус, инсайдеры, новости).

Ветка разбора агрегатор не использует: её работу выполняет `ReportEngine` по шаблону (см. D12), иначе логика отчёта снова оказалась бы зашита в один инструмент.


### D4. Набор инструментов у модели — по профилю сценария

Привязка инструментов остаётся компактной:

| Профиль | Что привязано | Когда |
|---|---|---|
| `lookup` | точечные инструменты (цена, дивиденды, фундаментал, новости, справочники) | `data_lookup`, `security_analysis` |
| `review` | агрегатор разбора + 6–8 инструментов добора | `portfolio_review` |
| `none` | ничего | после готового отчёта или при отказе |

Альтернатива — привязать все ~54 инструмента: превышает практические лимиты функций у провайдеров и резко ухудшает выбор инструмента. Отклонено.

### D5. Числа считает код, модель — интерпретацию

Отчёт делится на два слоя:

- **Факты** (секции 1–8: снимок, структура, концентрация, динамика, новости, аналитика, налоги, пробелы) — формируются кодом из собранных данных, как сейчас `formatPortfolioReport`.
- **Интерпретация** (фаза цикла, секторы-бенефициары, итог и совет) — генерируется моделью по компактному «брифингу»: топ-факты, доли, изменения, заголовки новостей. Брифинг ограничен по объёму, чтобы уложиться в таймаут.

Если модель недоступна или вернула пустой ответ, отчёт отдаётся без интерпретации с явной пометкой и `partial: true`. Сырые JSON инструментов в контекст модели не попадают — только брифинг.

### D6. Макро-контекст: ставка ЦБ из второго источника, остальное — оценка

В T-Invest MCP нет ставки ЦБ, инфляции и макро-календаря. Проверка источников: у ЦБ нет машиночитаемого JSON/XML — страница `hd_base/KeyRate` отдаёт HTML-таблицу и экспорт в PDF, `cbr-xml-daily.ru` содержит только курсы валют. Поэтому:

- **факты из брокера**: динамика индексов и отраслевых движений по секторам позиций;
- **факты из второго источника**: текущая ключевая ставка и история решений (адаптер `cbr` + сид-файл `data/key-rate-seed.json`, обновляемый скриптом);
- **оценка модели**: фаза цикла и секторы-бенефициары — с пометкой `(оценка)` и обязательным указанием, на каких фактах она построена;
- справочник «фаза цикла → типичные секторы» — статический текст в промпте, версионируется вместе с кодом.

Альтернативы: выдавать фазу цикла как «данные брокера» (недопустимая подмена источника) и парсить HTML ЦБ на каждом запросе (хрупко и медленно). Отклонены: сид + периодическое обновление, live-режим — опцией.

### D7. Налоговый контекст из операций и новостей

Налоговый тул в MCP отсутствует, поэтому раздел собирается из двух источников: `invest_get_operations` с фильтром по налоговым типам (удержанные налоги, налог по дивидендам и купонам) и новости по ключевым словам о налогообложении. Если нет ни того, ни другого — «налоговых данных в источниках нет» и никаких утверждений о ставках.

### D8. Дедупликация, параллельность, кэш

- В рамках прогона — `Map` ключ `tool + стабильный JSON args`; повторный запрос возвращает сохранённый результат.
- Независимые запросы идут пачками по `RUN_PARALLELISM`; записи с `priority: mandatory` выполняются первыми.
- Между прогонами кэшируются только справочники (сектор/бренд/тип бумаги), TTL 24 ч. Котировки, новости и прогнозы не кэшируются — отчёт должен быть про «сейчас».
- Ответ 429 от брокера — пауза и один повтор, затем источник считается недоступным.

### D9. Лимиты и дедлайны из конфигурации

Новые переменные со значениями по умолчанию: `RUN_TOOL_MAX_CALLS=40`, `RUN_DEADLINE_MS=90000`, `RUN_PARALLELISM=4`, `REVIEW_MAX_INSTRUMENTS=15`, `MCP_TOOL_TIMEOUT_MS=15000`, `REVIEW_ENABLED=true`.

Дедлайн действует на весь прогон, бюджет — общий на все вызовы, включая вызовы внутри агрегаторов (счётчик уже общий, менять механику не нужно). Частичный результат при исчерпании — как сейчас.

Решение по синхронности: прогон разбит на два HTTP-запроса (`chat` → `202` с планом, `chat/approve` → `200` с отчётом), поэтому дедлайн 90 с укладывается в клиентский таймаут. Асинхронные задания не вводятся.

### D10. Совместимость и обратимость

`REVIEW_ENABLED=false` возвращает прежнее поведение: две метки, сводка по счетам, старый бюджет. Это и фича-флаг, и путь откатa. Изменение значений `intent` помечено в `proposal.md` как BREAKING и переносится в `docs/api.md` до включения по умолчанию.

### D11. Разбор — новая ветка того же графа, а не второй агент

Выбран вариант «отдельная нода»: в существующем `StateGraph` появляется ветка `plan → collect → report`, в которую роутер отправляет только `portfolio_review`. Простые вопросы идут прежним путём (`answer ⇄ approve → tools`).

Почему не отдельный сервис или эндпоинт: один реестр MCP, одна политика подтверждений, одно состояние в SQLite, один чекпоинтер и одна точка наблюдаемости. Отдельный сервис потребовал бы дублировать discovery, allowlist, бюджет и трассировку, а также второй контейнер и вторую конфигурацию. Эндпоинт с `mode` смешал бы бюджеты и таймауты в одном контракте.

Что даёт нода: у ветки свой бюджет и дедлайн (`RUN_TOOL_MAX_CALLS`, `RUN_DEADLINE_MS` из конфигурации), свой профиль инструментов и своя точка отказа — сбой разбора не влияет на простые вопросы. Границы ветки видны в трейсе как отдельные спаны `plan`, `collect`, `report`.

### D12. Логика отчёта — шаблон + движок + реестр поставщиков

Отчёт собирается не кодом «под сценарий», а движком по шаблону:

- **Шаблон** (`reports/portfolio-review.yaml`) — секции с `id`, `title`, `provider`, `render`, `params`, `interpret`. Здесь же пороги концентрации, целевые доли и набор периодов.
- **Поставщики фактов** (`fact providers`) — реестр функций: `portfolio.snapshot`, `portfolio.structure`, `portfolio.gaps`, `market.dynamics`, `market.analytics`, `news.digest`, `tax.context`, `macro.context`, `facts.brief`. Каждый возвращает типизированные факты или «нет данных».
- **Движок** (`ReportEngine`) — валидирует шаблон, собирает факты, рендерит секции, отдаёт markdown и структурированный JSON, помечает недоступное, подставляет `templateVersion`.
- **Интерпретация** — только секции с `interpret: true`, одним вызовом модели на брифинге.

Альтернативы: зашитый рендер в коде (каждая правка отчёта — релиз) и внешний шаблонизатор с логикой в шаблоне (превращается в язык программирования, невозможно валидировать). Отклонены.

Важно: план сбора (`D1`) выводится из шаблона — какие providers нужны, столько и запросов. Убрали секцию из шаблона — перестали ходить за её данными.

### D13. Хранение и выгрузка отчётов

Отчёт сохраняется в состоянии с `reportId` (UUID), содержит markdown, структурированный JSON и `templateVersion`. Выгрузка — `GET /api/v1/reports/:reportId?format=md|json|html`. Хранение — та же SQLite, TTL как у сессий (`STATE_TTL_DAYS`). Отчёт привязан к `USER_ID`: чужой `reportId` отдаёт `404`, чтобы не раскрывать данные.

Альтернатива — генерировать отчёт только в ответе чата, без сохранения: нельзя переоткрыть, сравнить версии и выгрузить в другом формате. Отклонено.

### D14. Тематические инструменты и реестр источников

Три уровня, каждый со своей зоной ответственности:

```
Тематический инструмент (что видит LLM)   market__news_digest
   └─ провайдер фактов (что видит шаблон) news.digest
        └─ источник (откуда данные)       tinkoff.news │ external.news
```

Правила:

- имя инструмента — `<тема>__<действие>`, темы: `portfolio`, `security`, `market`, `macro`;
- инструмент не знает, откуда пришли данные: он зовёт провайдера, провайдер — все включённые источники темы;
- источник объявляет `id`, темы, обязательную конфигурацию, TTL кэша и признак «медленноменяющиеся данные»;
- добавление источника = новый файл-адаптер + строка конфигурации; шаблон отчёта и граф не меняются;
- старые имена (`portfolio_all_accounts`, `price_dynamics`) живут как алиасы один релиз, чтобы правила подтверждений и промпты не сломались.

Итоговый набор инструментов:

| Инструмент | Тема | Источники |
|---|---|---|
| `portfolio__snapshot` | portfolio | tinkoff |
| `portfolio__review` | portfolio | tinkoff |
| `security__brief` | security | tinkoff |
| `market__price_dynamics` | market | tinkoff |
| `market__news_digest` | market | tinkoff.news (+ внешние) |
| `market__tax_watch` | market | tinkoff.news, tinkoff.operations |
| `macro__key_rate` | macro | cbr (live или сид) |

### D15. Ставка ЦБ: SOAP ЦБ как live, кэш и сид как страховка

У ЦБ **есть** машиночитаемый интерфейс: SOAP-метод `KeyRateXML(fromDate, ToDate)` службы `DailyInfo` (`https://www.cbr.ru/DailyInfoWebServ/DailyInfo.asmx`, SOAPAction `http://web.cbr.ru/KeyRateXML`). Это снимает необходимость парсить HTML. Цепочка получения:

1. **live** — SOAP-вызов `KeyRateXML` за нужный период;
2. **кэш** в SQLite с `KEY_RATE_CACHE_TTL_HOURS` (24 ч) — ставка меняется 6–8 раз в год, чаще ходить незачем;
3. **сид** `data/key-rate-seed.json` — история решений, обновляется `scripts/fetch-key-rate.mjs` тем же SOAP-методом (приём как у `scripts/fetch-mcp-ca.mjs`);
4. **HTML-таблица** `hd_base/KeyRate` — резервный парсер, если SOAP недоступен, а кэш и сид устарели.

`KEY_RATE_SOURCE_MODE=live|seed|off` (по умолчанию `live`): `live` — цепочка 1→2→3→4, `seed` — только файл, `off` — секция макро честно сообщает об отсутствии данных. Время данных показывается всегда: «ставка 14,00 %, действует с 27.07.2026, получено 04.11.2026 из ЦБ».

Почему не «парсим HTML всегда»: вёрстка меняется, страница отдаёт только запрошенный диапазон, а отчёт не должен зависеть от доступности cbr.ru. Почему не только сид: данные стареют между обновлениями, а ставка — ключевой вход для оценки цикла.

### D16. Налоги: словарь вместо хардкода

`market__tax_watch` = факты удержаний из `invest_get_operations` (типы `OPERATION_TYPE_TAX`, `DIVIDEND_TAX`, `COUPON_TAX` и родственные) + новости, отфильтрованные по словарю `data/tax-keywords.yaml` (НДФЛ, НК РФ, вычет, ИИС, ЛДВ, прогрессивная шкала…). Словарь — файл данных, расширяется без правок кода. Ограничение честно фиксируется в отчёте: общая новостная лента без фильтра по дате, поэтому сканируется ограниченное число страниц (`NEWS_SCAN_PAGES`), а период определяется по дате публикации.

## Risks / Trade-offs

- Рост числа вызовов брокера → пачки по `RUN_PARALLELISM`, повтор с паузой на 429, лимит бумаг для расширенной аналитики, бюджет из конфигурации.
- Долгий прогон на большом портфеле → дедлайн 90 с, приоритеты обязательных источников, отчёт по собранному с `partial: true`.
- Ограничение контекста модели → брифинг вместо сырых JSON, интерпретация отдельным вызовом на компактном входе.
- Интерпретация (цикл, секторы, совет) может быть неточной → маркировка `(оценка)`, расширенный дисклеймер, запрет на конкретные сделки.
- Регрессия текущих сценариев → фича-флаг, существующие unit/e2e тесты как регрессия, отчёт сводки по счетам не переписывается.
- Стоимость LLM растёт из-за второго вызова на интерпретацию → один вызов интерпретации на разбор, краткий вход, отсутствие интерпретации для `data_lookup`.
- Новости без фильтра по дате в API → периоды определяются по дате новости в ответе, объём ограничивается `limit` и пагинацией.

## Migration Plan

1. Расширить `MCP_TINKOFF_ALLOWED_TOOLS` и `.env.example`; при старте — предупреждение о read-only инструментах каталога, не попавших в allowlist.
2. Добавить лимиты в zod-схему и `AppConfigService`; старые значения бюджета оставить дефолтами.
3. Ввести слои сбора и поставщиков фактов, не меняя граф: данные собираются, но ветки разбора ещё нет.
4. Добавить шаблон отчёта, `ReportEngine` и хранение отчётов с `reportId`; проверить сборку отчёта на фикстурах.
5. Ввести четыре метки и ветку `plan → approve → collect → report`; обновить `docs/api.md`.
6. Включить групповое подтверждение и блок `plan` в payload.
7. Включить `REVIEW_ENABLED=true` по умолчанию после прогона на живом портфеле.

Откат: `REVIEW_ENABLED=false` (поведение MVP) либо возврат прежнего `MCP_TINKOFF_ALLOWED_TOOLS`. Состояние в SQLite не меняет схему, миграция не нужна.
