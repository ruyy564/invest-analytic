# Design

## Context

См. proposal.md — Why. Текущее состояние, важное для решений:

- шаблон отчёта (`reports/portfolio-review.yaml`) помечает разделы `macro`, `opinions`,
  `verdict` как `interpret: true`; текст для них пишет модель по «брифингу» из `FactContext`;
- провайдеры фактов (`src/report/providers/*`) уже отдают `brief` и `structured`, поэтому
  секторы портфеля доступны движку без новых запросов;
- данные-файлы проекта (`data/ticker-aliases.yaml`, `data/tax-keywords.yaml`) читаются
  напрямую и деградируют молча — тот же подход годится для базы знаний;
- в проекте есть собственный разборщик YAML-подмножества (`src/report/yaml.ts`), внешняя
  зависимость не нужна;
- справочные вопросы сейчас уходят в `off_topic`, потому что область ассистента описана
  промптом и эвристиками без инвестиционных понятий;
- отключение ветки делается флагом (`AGENT_HELP_ENABLED`, `NEWS_FEED_ENABLED`) и передачей
  признака в `buildAgentGraph`.

## Goals / Non-Goals

**Goals:**

- база знаний как данные: состав и формулировки меняются без правки кода;
- одинаковый отбор контекста для разбора и для агента (одна функция, разные фильтры);
- жёсткая граница «знания — принципы, числа — из брифинга»;
- предсказуемый объём контекста модели (лимит символов, целые темы/тезисы);
- справочный ответ без данных, модели и подтверждения.

**Non-Goals:**

- не превращаем сервис в инвестиционного советника: никаких персональных рекомендаций;
- не храним и не докачиваем внешнюю аналитику (БКС и книги — только ссылки на источники);
- не учим базу знаний на данных пользователя (никакой персонализации содержимого);
- не заменяем `smartlab_tag`/новости: знания — контекст, а не лента;
- не делаем векторный поиск: отбор по тегам и ключевым словам достаточен для 12–15 тем.

## Decisions

**1. Формат — YAML-список тем, парсится существующим `parseYaml`.**
Тема: `id`, `title`, `summary`, `points[]`, `sections[]`, `sectors[]`, `keywords[]`, `sources[]`.
`summary` — определение в 1–2 предложения (его цитирует справочный ответ), `points` — короткие
тезисы. Альтернатива — markdown-файлы по темам: удобнее писать, но требует парсинга заголовков
и не даёт тегов для отбора; JSON исключён — в проекте уже YAML.

**2. Отбор — по тегам, а не по всему тексту.** `selectKnowledge(base, { section, sectors, question })`:
сначала темы, у которых `sections` содержит раздел, затем `sectors` пересекается с секторами
портфеля, затем `keywords` встречается в вопросе. Дедупликация по `id`, порядок стабилен
(порядок файла), лимит — по количеству тем и символам.

**3. Контекст встраивается в `interpretation` движка, а не в node.** В `InterpretationRequest`
добавляется поле `knowledge`; `buildReport` заполняет его из базы, переданной в
`BuildReportDeps.knowledge`, используя `structured.bySector` секции структуры. Так модель
получает блок через `createReportNode` без новых зависимостей в движке и без изменений
провайдеров. Альтернатива — читать файл внутри `engine.ts`: смешивает I/O с расчётом фактов.

**4. Секторы для отбора берутся из уже собранной структуры.** Если структуры нет (разбор
бумаги), сектор определяется по единственной бумаге из `securities.detail.structured`.
Иначе разделы `opinions` в разборе бумаги остались бы без темы сектора.

**5. Агент получает чек-лист, а не всю базу.** В системный промпт добавляется блок
`decision-checklist` + правило про оценки, ограниченный `KNOWLEDGE_MAX_CHARS` и выбранный
по одной теме. Полная база в промпте вытеснила бы инструкции и увеличила бы стоимость вызова;
для остальных тем есть справочная ветка.

**6. Справочный ответ — отдельная ветка `knowledge`, а не ответ модели.** Новый интент
`knowledge_question` определяется правилом до модели: вопрос содержит «что такое», «объясни»,
«расскажи про» и термин, совпавший с `keywords`/`title` темы. Ответ собирается кодом: заголовок,
определение, 3–5 тезисов, источник, напоминание об информационном характере. Модель не
вызывается — определения не «плывут» и не выдумываются. Если термин не найден — ответ
перечисляет доступные темы.

**7. Деградация без исключений.** Загрузчик возвращает пустую базу при отсутствии файла,
нечитаемом YAML или несоответствии схеме; причина пишется в лог один раз на старте.
Пустая база = отсутствие блока знаний, поведение прежнее.

**8. Флаги и конфигурация.** `KNOWLEDGE_ENABLED` (default `true`), `KNOWLEDGE_FILE`
(default `data/knowledge`), `KNOWLEDGE_FILE` (дополнительный файл-тема, необязательный),
`KNOWLEDGE_MAX_CHARS` (default 1800, минимум 400).
Признак передаётся в `buildAgentGraph` как `knowledgeEnabled`, база — как `knowledge` (загрузка
один раз в `agent-runtime.ts`/модуле Nest).

## Risks / Trade-offs

- **Модель использует знания вместо фактов** → в промпт интерпретации добавляется правило
  «справочный блок — только для трактовки; числа только из брифинга», тема `decision-checklist`
  требует пометки оценок.
- **Раздувание промпта и рост стоимости** → лимит символов, не более 3 тем на раздел,
  в агентский промпт — только чек-лист.
- **Устаревание фактов в базе (ставки, события)** → в базе нет текущих значений: исторические
  примеры помечены как исторические, источники указываются списком.
- **Ошибки в исторических данных** → формулировки качественные (без точных цифр доходности),
  книги и БКС указаны как источники, а не как «данные брокера».
- **Ложное распознавание справочного вопроса** («что такое мой портфель») → правило требует
  совпадения с термином базы знаний, а портфельные маркеры (`портфель`, `счёт`, тикер) идут
  раньше и перехватывают вопрос.
- **Расхождение ответов справки и базы** → перечень возможностей строится из одной карты
  `capabilities.ts`, новая возможность добавляется туда с флагом `requiresKnowledge`.

## Migration Plan

1. Добавить файл базы и модуль загрузки; поведение не меняется, пока флаг выключен.
2. Включить `KNOWLEDGE_ENABLED=true`: разделы получают справочный блок, агент — чек-лист.
3. Откат — `KNOWLEDGE_ENABLED=false` (блок и справочная ветка исчезают, вопросы про понятия
   снова уходят в общий маршрут).
