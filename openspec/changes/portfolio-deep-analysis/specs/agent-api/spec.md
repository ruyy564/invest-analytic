# Spec Delta

## MODIFIED Requirements

### Requirement: Приём вопроса через чат-эндпоинт

Сервис SHALL принимать вопрос по `POST /api/v1/agent/chat` и возвращать `status`, `answer`, `requestId`, `sessionId`, `intent`, `partial`, `report` и `traceUrl`.

#### Scenario: Ответ без чтения данных

- **WHEN** клиент отправляет вопрос, для ответа на который не нужны инструменты
- **THEN** сервис отвечает `200` со `status: "completed"` и полями `answer`, `requestId`, `sessionId`, `intent`, `partial`, `report`, `traceUrl`

#### Scenario: Новый клиент без сессии

- **WHEN** клиент не передаёт `sessionId`
- **THEN** сервис создаёт новую сессию и возвращает её идентификатор в ответе

#### Scenario: Продолжение сессии

- **WHEN** клиент передаёт `sessionId` из предыдущего ответа
- **THEN** сервис обрабатывает вопрос в той же сессии и возвращает тот же `sessionId`

### Requirement: Ответ при ожидании подтверждения

Сервис SHALL возвращать `202` со `status: "awaiting_approval"` и описанием ожидаемого решения, когда прогон остановлен на подтверждении плана чтений.

#### Scenario: Требуется подтверждение

- **WHEN** прогон остановился в узле `approve`
- **THEN** сервис отвечает `202` с `status`, `sessionId`, `requestId` и полем `approval`, содержащим вопрос, перечень планируемых чтений, их число и затрагиваемые счета, без секретов

## ADDED Requirements

### Requirement: Значения intent в ответе

Поле `intent` SHALL принимать значения `data_lookup`, `security_analysis`, `portfolio_review` и `off_topic` и SHALL совпадать с меткой, определившей сценарий прогона.

#### Scenario: Разбор портфеля

- **WHEN** пользователь просит проанализировать портфель
- **THEN** ответ содержит `intent: "portfolio_review"`

#### Scenario: Посторонний вопрос

- **WHEN** вопрос вне области агента
- **THEN** ответ содержит `intent: "off_topic"` и `status: "completed"`

### Requirement: Метаданные отчёта в ответе

Ответ SHALL содержать блок `report` с идентификатором отчёта, видом ответа, временем сбора данных и перечнем источников со статусом получен или недоступен.

#### Scenario: Полный разбор

- **WHEN** разбор портфеля собран полностью
- **THEN** `report` содержит идентификатор отчёта, вид ответа, время сбора и все источники со статусом «получен»

#### Scenario: Частичный разбор

- **WHEN** часть источников недоступна
- **THEN** `report` содержит недоступные источники с причиной, а `partial` равно `true`

### Requirement: Выгрузка отчёта по идентификатору

Сервис SHALL отдавать сохранённый отчёт по `GET /api/v1/reports/:reportId` в формате `md`, `json` или `html` и MUST отвечать `404` с единым форматом ошибки на неизвестный идентификатор.

#### Scenario: Выгрузка в markdown

- **WHEN** клиент запрашивает отчёт с `format=md`
- **THEN** сервис возвращает текст отчёта с типом содержимого markdown

#### Scenario: Неизвестный отчёт

- **WHEN** клиент запрашивает несуществующий `reportId`
- **THEN** сервис отвечает `404` и `{"error": {"code": "REPORT_NOT_FOUND", ...}}` без внутренних деталей

#### Scenario: Отчёт другого пользователя

- **WHEN** запрошен отчёт, не принадлежащий текущему `USER_ID`
- **THEN** сервис отвечает `404` и не раскрывает содержимое

### Requirement: Совместимость кодов ответа

Сервис SHALL сохранять коды `200`, `202`, `400`, `409`, `410`, `500`, `503` и единый формат ошибок при изменении состава полей ответа.

#### Scenario: Ожидание подтверждения

- **WHEN** прогон ждёт решения по плану
- **THEN** сервис по-прежнему отвечает `202`

#### Scenario: Подтверждение истекло

- **WHEN** подтверждение пришло позже `APPROVAL_TTL_MINUTES`
- **THEN** сервис отвечает `410` с кодом `APPROVAL_EXPIRED` и не продолжает прогон
