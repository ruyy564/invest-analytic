# approval-policy Specification

## Purpose
Определяет единый декларативный источник правил о том, какие действия агента требуют подтверждения, чтобы список менялся в одном файле без правок графа, роутеров и узлов.

## Requirements

### Requirement: Единый файл правил подтверждения
Правила MUST быть объявлены в одном файле правил, а код графа, роутеров и узлов MUST NOT содержать собственного перечня инструментов, требующих подтверждения.

#### Scenario: Добавление нового правила
- **WHEN** в файл правил добавлено правило для инструмента
- **THEN** агент начинает требовать подтверждение для этого инструмента без изменений в коде графа

#### Scenario: Код не дублирует перечень
- **WHEN** разработчик ищет перечень подтверждаемых инструментов
- **THEN** единственное место объявления — файл правил

### Requirement: Схема правила
Каждое правило SHALL содержать шаблон имени инструмента, короткое название действия, текст вопроса пользователю и признак обязательности подтверждения.

#### Scenario: Полное правило
- **WHEN** правило содержит `tool`, `label`, `question`, `requiresApproval`
- **THEN** вопрос подтверждения формируется из `question`, а список действий — из `label` и аргументов вызова

#### Scenario: Правило без обязательных полей
- **WHEN** в правиле отсутствует `label` или `question`
- **THEN** старт завершается ошибкой конфигурации с указанием правила

### Requirement: Сопоставление правил с инструментами
Сервис SHALL сопоставлять инструмент с правилами по полному имени или шаблону с `*` и применять первое совпавшее правило.

#### Scenario: Точное совпадение
- **WHEN** вызывается `tinkoff__invest_get_portfolio` и есть правило с этим именем
- **THEN** применяется это правило

#### Scenario: Шаблон
- **WHEN** есть правило `tinkoff__invest_*` и вызывается `tinkoff__invest_get_positions`
- **THEN** применяется правило-шаблон

### Requirement: Поведение для не перечисленных действий

Для инструментов без правила сервис SHALL применять политику `APPROVAL_UNLISTED` (`require` по умолчанию, `allow` как явное исключение) и SHALL включать такой инструмент в план чтений, если политика требует подтверждения.

#### Scenario: Новый инструмент без правила

- **WHEN** в реестре MCP появился инструмент, которого нет в правилах, и он попал в план сбора
- **THEN** он входит в запрос подтверждения плана и не вызывается до решения пользователя

#### Scenario: Явное разрешение без подтверждения

- **WHEN** в правиле указано `requiresApproval: false`
- **THEN** инструмент вызывается без отдельного подтверждения, в том числе в составе плана

### Requirement: Проверка правил при старте
Сервис SHALL проверять правила при запуске и MUST NOT стартовать при дубликатах, отсутствии обязательных полей, ссылке на неизвестный инструмент или разрешении торгового инструмента без подтверждения.

#### Scenario: Опечатка в имени инструмента
- **WHEN** правило ссылается на инструмент, которого нет в реестре MCP
- **THEN** старт завершается ошибкой с указанием правила и имени инструмента

#### Scenario: Торговый инструмент без подтверждения
- **WHEN** правило разрешает торговый инструмент с `requiresApproval: false`
- **THEN** старт завершается ошибкой конфигурации

### Requirement: Внешний файл правил
Сервис SHALL поддерживать загрузку правил из файла, указанного в `APPROVALS_FILE`, валидировать его той же схемой и MUST заменять встроенный набор целиком.

#### Scenario: Правила заданы файлом
- **WHEN** задан `APPROVALS_FILE` с корректным JSON
- **THEN** используются правила из файла, а встроенный набор не применяется

#### Scenario: Некорректный файл правил
- **WHEN** файл по `APPROVALS_FILE` не найден или не проходит схему
- **THEN** старт завершается ошибкой конфигурации с указанием пути и причины

### Requirement: Групповое подтверждение плана чтений

Сервис SHALL запрашивать подтверждение один раз на прогон — на весь план чтений, и MUST NOT останавливать прогон повторно на каждом вызове того же плана.

#### Scenario: План из нескольких источников

- **WHEN** план разбора портфеля содержит цены, дивиденды, фундаментал, прогнозы и новости
- **THEN** пользователь получает один запрос подтверждения на весь план и одно решение

#### Scenario: Повторный вопрос в той же сессии

- **WHEN** пользователь задаёт новый вопрос, требующий чтения данных
- **THEN** подтверждение запрашивается заново, ранее данное согласие не переносится

### Requirement: Состав запроса подтверждения по плану

Запрос подтверждения SHALL содержать текст вопроса, перечень планируемых чтений с короткими названиями действий, число запросов и затрагиваемые счёта, без секретов и без полного каталога инструментов.

#### Scenario: Разбор портфеля

- **WHEN** план содержит двадцать чтений по трём счетам
- **THEN** запрос подтверждения перечисляет планируемые чтения по видам данных и указывает число запросов и счетов

#### Scenario: Точечный вопрос

- **WHEN** план содержит одно чтение по одной бумаге
- **THEN** запрос подтверждения содержит название действия и параметры этого чтения

### Requirement: Отказ от плана

При отказе пользователя сервис SHALL не выполнять ни одного чтения плана и MUST сообщить, какие данные не были получены.

#### Scenario: Пользователь отказал

- **WHEN** пользователь отклоняет подтверждение плана
- **THEN** ни один запрос плана не выполняется, а ответ объясняет, что данные не читались, и предлагает подтвердить запрос

### Requirement: Незавершённый сбор при подтверждённом плане

Если часть чтений плана завершилась ошибкой после подтверждения, сервис MUST NOT запрашивать подтверждение заново на те же чтения.

#### Scenario: Ошибка источника после подтверждения

- **WHEN** подтверждённый план частично не выполнен из-за ошибок брокера
- **THEN** ответ формируется по собранным данным и сообщает о недоступных источниках без второго запроса подтверждения

### Requirement: Новостная ветка без подтверждения

Сервис SHALL выполнять чтение публичных новостных источников без запроса
подтверждения, поскольку эти данные не относятся к счёту и портфелю
пользователя. Подтверждение MUST оставаться обязательным для любого чтения
портфеля, операций и справочников бумаг пользователя.

#### Scenario: Вопрос про новости рынка

- **WHEN** пользователь спрашивает последние новости инвестиционного рынка
- **THEN** подтверждение не запрашивается, ответ формируется сразу
- **AND** значения `status` в ответе равно `completed`

#### Scenario: Вопрос про состав портфеля

- **WHEN** пользователь просит данные своего портфеля
- **THEN** подтверждение запрашивается как раньше
- **AND** без подтверждения данные не читаются

#### Scenario: Новости и портфель в одном вопросе

- **WHEN** вопрос просит и новости рынка, и данные портфеля
- **THEN** прогон идёт по сценарию портфеля с подтверждением
- **AND** новостная ветка без подтверждения не используется
