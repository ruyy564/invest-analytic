# state-persistence Specification

## Purpose
Хранит состояние прогонов и общие данные между перезапусками сервиса, чтобы история сессий и ожидающие подтверждения не терялись, а бэкенд хранилища выбирался конфигурацией.

## Requirements

### Requirement: Персистентное состояние прогонов
Сервис SHALL сохранять состояние каждого прогона по `sessionId` в постоянное хранилище и восстанавливать его после перезапуска сервиса.

#### Scenario: Продолжение сессии после перезапуска
- **WHEN** клиент продолжает сессию после перезапуска сервиса
- **THEN** агент видит предыдущие сообщения сессии и отвечает с их учётом

#### Scenario: Ожидающее подтверждение переживает перезапуск
- **WHEN** сервис перезапустился, пока сессия ожидала подтверждения
- **THEN** подтверждение по этой сессии продолжает прогон с места остановки

### Requirement: Выбор бэкенда хранилища
Сервис SHALL выбирать хранилище состояния по `STATE_BACKEND` (`sqlite` по умолчанию, `memory` для тестов) и путь к файлу — по `STATE_SQLITE_PATH`.

#### Scenario: Значение по умолчанию
- **WHEN** `STATE_BACKEND` не задан
- **THEN** сервис использует SQLite по пути из `STATE_SQLITE_PATH`

#### Scenario: In-memory режим
- **WHEN** `STATE_BACKEND=memory`
- **THEN** состояние живёт только в процессе и не переживает перезапуск, что используется в тестах

#### Scenario: Неизвестный бэкенд
- **WHEN** `STATE_BACKEND` содержит неподдерживаемое значение
- **THEN** старт завершается ошибкой конфигурации со списком поддерживаемых значений

### Requirement: Глобальное хранилище общих данных
Сервис SHALL хранить данные, общие для всех сессий (например, счёт по умолчанию), в отдельном глобальном хранилище, доступном во всех сессиях и после перезапуска.

#### Scenario: Счёт по умолчанию
- **WHEN** счёт был сохранён в глобальном хранилище
- **THEN** новая сессия использует его без повторного запроса списка счетов

#### Scenario: Глобальные данные переживают перезапуск
- **WHEN** сервис перезапускается
- **THEN** ранее сохранённые общие данные остаются доступными

### Requirement: Запрет кэширования данных портфеля
Сервис MUST NOT сохранять в глобальном хранилище состав портфеля, позиции и суммы, чтобы чтение данных брокера всегда шло через подтверждение.

#### Scenario: Ответ по портфелю после перезапуска
- **WHEN** пользователь спрашивает о портфеле в новой сессии
- **THEN** данные запрашиваются у брокера после подтверждения, а не берутся из глобального хранилища

### Requirement: Изоляция пространств имён
Сервис SHALL разделять данные хранилища по пространствам имён (`USER_ID`, области `session` и `global`) и MUST NOT отдавать данные одного пространства в другом.

#### Scenario: Разные пользователи
- **WHEN** сервис настроен на разных `USER_ID`
- **THEN** глобальные данные одного пользователя не видны другому

### Requirement: Очистка устаревших сессий
Сервис SHALL удалять состояние сессий, не обновлявшихся дольше `STATE_TTL_DAYS`, при старте и MUST NOT восстанавливать удалённые сессии.

#### Scenario: Устаревшая сессия
- **WHEN** сессия не обновлялась дольше установленного срока
- **THEN** её состояние удаляется при старте, а новый запрос с этим `sessionId` начинается с чистого состояния
