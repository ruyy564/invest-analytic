# data-sources Specification

## Purpose
Определяет устройство тематических инструментов агента и реестра источников данных: как инструменты группируются по темам, как несколько источников сливаются в один ответ, как настраивается приоритет, кэш и деградация, и как добавить тему или источник без правок графа и отчёта.

## Requirements

### Requirement: Тематические пространства имён инструментов

Локальные инструменты SHALL называться `<тема>__<действие>` с темами `portfolio`, `security`, `market`, `macro` и MUST NOT быть свалкой имён без префикса.

#### Scenario: Инструменты по темам

- **WHEN** агент получает набор локальных инструментов
- **THEN** имена сгруппированы по темам: `portfolio__snapshot`, `portfolio__review`, `security__brief`, `market__news_digest`, `market__tax_watch`, `macro__key_rate`

#### Scenario: Новая тема

- **WHEN** добавляется тема `macro` с новым инструментом
- **THEN** она появляется в наборе, а существующие темы и их инструменты не меняются

### Requirement: Тонкий инструмент над реестром источников

Каждый тематический инструмент SHALL быть обёрткой над реестром источников и MUST NOT содержать логики конкретного источника внутри себя.

#### Scenario: Инструмент без привязки к источнику

- **WHEN** разработчик добавляет второй новостной источник
- **THEN** код инструмента новостей не меняется — регистрируется новый источник

#### Scenario: Единственный источник темы

- **WHEN** для темы доступен один источник
- **THEN** инструмент возвращает его данные с указанием источника

### Requirement: Реестр источников с обязательной конфигурацией

Каждый источник SHALL объявлять идентификатор, обслуживаемые темы и обязательные параметры конфигурации; включённый источник без конфигурации MUST приводить к ошибке конфигурации при старте.

#### Scenario: Источник без конфигурации

- **WHEN** источник ЦБ включён, но адрес источника не задан
- **THEN** старт завершается ошибкой конфигурации с указанием переменной

#### Scenario: Источник отключён

- **WHEN** источник отключён в конфигурации
- **THEN** его данные не запрашиваются, а тема работает с оставшимися источниками

### Requirement: Слияние нескольких источников

При нескольких источниках одной темы сервис SHALL объединять результаты, удалять дубликаты, указывать источник для каждого элемента и сортировать общую повестку по свежести.

#### Scenario: Два новостных источника

- **WHEN** включены два источника новостей и они вернули одну и ту же публикацию
- **THEN** в сводке она встречается один раз, а источник указан по правилу приоритета

#### Scenario: Атрибуция

- **WHEN** сводка собрана из двух источников
- **THEN** рядом с каждым элементом и в метаданных покрытия указано, откуда он получен

#### Scenario: Общая повестка без фильтра по бумагам

- **WHEN** запрос новостей не называет тикеров и портфеля
- **THEN** опрашиваются все источники темы новостей, включая ленты и каналы
- **AND** результат объединяется в один список, отсортированный от новых публикаций к старым

#### Scenario: Отказ одного источника при общей повестке

- **WHEN** один из источников общей повестки не ответил
- **THEN** остальные источники попадают в сводку
- **AND** отказавший источник отмечен в покрытии с причиной

### Requirement: Приоритет источников конфигурацией

Сервис SHALL задавать порядок источников конфигурацией и MUST NOT менять его без явного указания в настройках.

#### Scenario: Изменён приоритет

- **WHEN** в конфигурации первым указан другой источник новостей
- **THEN** при дублировании публикации атрибуция берётся из него, правок кода не требуется

### Requirement: Кэш по типу данных

Сервис SHALL кэшировать медленноменяющиеся данные (ключевая ставка, справочники) с настраиваемым TTL и MUST NOT кэшировать котировки, новости и прогнозы между прогонами.

#### Scenario: Ставка ЦБ из кэша

- **WHEN** второй прогон дня запрашивает ключевую ставку
- **THEN** значение берётся из кэша с указанием времени получения

#### Scenario: Новости не кэшируются

- **WHEN** два прогона подряд запрашивают новости
- **THEN** оба запроса уходят к источнику

### Requirement: Сид-файл для источника без стабильного API

Для источника, у которого нет стабильного машиночитаемого API, сервис SHALL поддерживать сид-файл данных и SHALL указывать в ответе, что данные взяты из сида.

#### Scenario: Источник недоступен, сид есть

- **WHEN** источник ключевой ставки недоступен, а сид-файл существует
- **THEN** инструмент возвращает данные сида с пометкой источника и времени сида

#### Scenario: Ни источника, ни сида

- **WHEN** источник недоступен и сид-файл отсутствует
- **THEN** инструмент возвращает «нет данных» с причиной, а не пустой список

### Requirement: Деградация на уровне источника

Недоступность одного источника MUST NOT ломать тему и MUST NOT подменять отсутствующие данные значением другого источника без указания подмены.

#### Scenario: Второй источник упал

- **WHEN** один из двух новостных источников вернул ошибку
- **THEN** сводка строится по оставшемуся, а покрытие содержит недоступный источник с причиной

### Requirement: Расширение без правок отчёта

Добавление источника или темы SHALL требовать только нового адаптера и правки конфигурации, без изменения шаблона отчёта и графа.

#### Scenario: Подключён новый источник ставки

- **WHEN** добавлен адаптер второго источника ключевой ставки
- **THEN** секция макро-контекста получает его данные без правок шаблона

#### Scenario: Новая тема в шаблоне

- **WHEN** в шаблоне появляется секция, ссылающаяся на поставщика новой темы
- **THEN** сбор идёт через тот же реестр источников

### Requirement: Адаптер лент для новостных источников

Сервис SHALL поддерживать источники-ленты с объявленным форматом (`rss`, `atom`, `soap-xml`, `json`) и объявленным маппингом полей (заголовок, ссылка, дата, текст, теги) и MUST NOT требовать отдельного кода на каждую новую ленту.

#### Scenario: Новая RSS-лента

- **WHEN** в конфигурацию добавлены адрес ленты, формат `rss` и маппинг полей
- **THEN** новости этой ленты попадают в `market__news_digest` без правок кода

#### Scenario: Лента отдала не тот формат

- **WHEN** по адресу RSS ожидается XML, а приходит HTML
- **THEN** источник помечается некорректным с причиной, а сводка строится без него

#### Scenario: Пустая или битая лента

- **WHEN** лента вернула пустой список или невалидный XML
- **THEN** источник считается недоступным, прогон продолжается

### Requirement: Совместимость имён инструментов

При переименовании локальных инструментов в тематический вид сервис SHALL сохранять старые имена как алиасы на время миграции.

#### Scenario: Старое имя в правилах

- **WHEN** правило подтверждения или промпт ссылается на старое имя `portfolio_all_accounts`
- **THEN** вызов по старому имени работает и маппится на `portfolio__snapshot`

### Requirement: Конвейер обработки источника

Сервис SHALL обрабатывать источник стадиями: получение, извлечение полей, приведение к каноническому виду, применение политики, устранение дублей, ранжирование, отбор и представление.

#### Scenario: Новый источник

- **WHEN** подключается новый источник
- **THEN** он реализует получение и извлечение, а остальные стадии переиспользуются без изменений

#### Scenario: Стадии разделены

- **WHEN** изменяется правило релевантности
- **THEN** правится только политика, а получение и извлечение остаются нетронутыми

### Requirement: Канонический элемент данных

Каждый элемент SHALL приводиться к единой схеме с обязательными полями: идентификатор, заголовок, время публикации в ISO 8601, источник, признаки привязки к бумаге и необязательные аннотация и ссылка.

#### Scenario: Элемент без даты

- **WHEN** источник отдал элемент без корректной даты
- **THEN** элемент отбрасывается с причиной, а остальные элементы источника сохраняются

#### Scenario: Привязка к бумаге

- **WHEN** источник помечает элемент тегами инструментов
- **THEN** привязка хранится отдельно от рубрик и используется политикой релевантности

### Requirement: Политика релевантности как данные

Правила отбраковки (общие сводки, темы вне инвестиционной повестки, маркеры релевантности, правила привязки к бумаге) SHALL храниться в версионируемом файле данных и MUST NOT быть зашиты в код источников.

#### Scenario: Изменение правила

- **WHEN** требуется отбросить новый класс нерелевантных заголовков
- **THEN** добавляется правило в файл политики, код не меняется

#### Scenario: Единая точка правды

- **WHEN** правило применяется к нескольким источникам
- **THEN** все источники используют одну и ту же версию политики

### Requirement: Отчёт стадий с причинами

Сервис SHALL формировать отчёт по стадиям: сколько элементов получено, сколько сохранено и сколько отброшено с указанием причины, и SHALL включать его в покрытие результата.

#### Scenario: Диагностика мусора в отчёте

- **WHEN** в итоговой выборке оказались нерелевантные элементы
- **THEN** в покрытии видно, на какой стадии и по какой причине они были пропущены или оставлены

#### Scenario: Пустая выборка

- **WHEN** после политики не осталось элементов
- **THEN** результат содержит отчёт стадий и причину пустоты, а не только признак отсутствия данных

### Requirement: Golden-тесты источников

Для каждого источника SHALL храниться зафиксированный ответ и SHALL существовать проверка, что извлечение даёт ожидаемое число элементов с ожидаемыми полями.

#### Scenario: Изменилась вёрстка источника

- **WHEN** извлечение перестаёт находить элементы в зафиксированном ответе
- **THEN** проверка источника падает до выпуска, а причина видна по имени источника

### Requirement: Шлюз внешних запросов

Получение данных из сети SHALL выполнять через общий шлюз с таймаутом, ограничением параллельности, повторами, резервным адресом и кэшем с заданным сроком жизни.

#### Scenario: Медленный источник

- **WHEN** источник не ответил за таймаут
- **THEN** шлюз прекращает ожидание, а источник помечается недоступным с причиной

#### Scenario: Повторный запрос в прогоне

- **WHEN** две бумаги запрашивают одну и ту же ленту
- **THEN** второй запрос обслуживается из кэша шлюза в пределах срока жизни
