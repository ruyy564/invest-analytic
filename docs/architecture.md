# Архитектура сервиса

Документ фиксирует правила, по которым развивается кодовая база: границы модулей,
контракты расширения (инструменты, MCP, источники, провайдеры фактов, узлы графа,
база знаний) и то, как всё это переиспользовать, не ломая соседей.

Правила ниже проверяемы: если изменение им противоречит, это повод обсудить
исключение, а не тихо его обойти.

## 1. Принципы

1. **Модуль = бизнес-возможность, а не тип файла.** `agent`, `report`, `knowledge`,
   `sources`, `tools`, `state`, `api`, `llm`, `config` — вертикальные срезы. Внутри
   модуля допустимы любые папки (`nodes`, `providers`, `mappers`), между модулями —
   только публичный контракт.
2. **Слои внутри модуля, а не глобальные `domain/` и `infrastructure/`.** Внутри
   feature-модуля: контроллер (вход) → сервис (`@Injectable`, бизнес-логика) → провайдеры
   (репозиторий файлов, MCP, LLM, хранилище). Направление одно: верх знает о низе, низ — нет.
   Самые нижние зависимости подключаются через токены (`MCP_TOOLS`, `CHECKPOINTER`,
   `LLM_ANSWER_MODEL`), как в документации Nest по провайдерам.
3. **DI вместо `new`.** Сервис получает зависимости через конструктор; внешние
   зависимости — через токены (`MCP_TOOLS`, `CHECKPOINTER`, `LLM_ANSWER_MODEL`,
   `REPORT_PROVIDERS`). Фабрики узлов принимают зависимости параметром, а не читают
   глобальное состояние.
4. **Конфигурация — одна точка.** `process.env` читается только в `src/platform/config`.
   Всё остальное получает типизированный `AppConfigService` (или его срез) параметром.
5. **Чистые функции для расчётов, адаптеры для I/O.** Движок отчёта, отбор знаний,
   парсер YAML, мапперы — чистые функции без сети и диска: их можно тестировать без
   моков. Файлы, MCP, БД, LLM живут в адаптерах и репозиториях.
6. **Ошибки — часть контракта.** Доменные ошибки (`McpUnavailableError`,
   `RunBudgetExceededError`, `ConfigError`, `NotAwaitingApprovalError`) поднимаются
   вверх без потери причины, а в HTTP превращаются фильтром на границе.
7. **Деградация вместо падения.** Недоступный источник, пустой файл знаний, отсутствие
   ключа — это состояние, о котором система сообщает (coverage, «данных нет», лог),
   а не исключение посреди прогона.
8. **Наблюдаемость по умолчанию.** У каждого вызова инструмента есть длительность и
   результат; у прогона — бюджет; у отчёта — `asOf` и список недоступных источников.

## 3. Правила зависимостей

- Разрешённые импорты: `transports → agent, platform`; `agent → capabilities/*/index.ts, platform, shared`;
  `capabilities/x → platform, shared, capabilities/y/index.ts`; `platform → shared`; `shared → ничего, кроме node`.
- Запрещены: `capabilities → agent`, `platform → capabilities`, `platform/shared → agent`,
  импорт внутренних файлов чужой возможности (только `index.ts`).
- Циклические зависимости запрещены. Если появляется соблазн «просто импортировать
  тип» — выносите контракт в отдельный модуль-контракт (`types.ts`, `*.interface.ts`).
- Общий тип между слоями (`CoverageEntry`, `SourceItem`, `FactContext`) живёт там,
  где он рождён, и импортируется как `import type` — без side-effect.
- Правила проверяет `test/unit/architecture.spec.ts`: нарушение ломает сборку.

## 4. Раскладка по файлам (Nest + LangGraph)

Правило простое: **файл делает одну вещь и остаётся маленьким**. Ориентиры — по строкам
кода: сервис/узел до ~120, тул до ~40, вспомогательный модуль до ~80. Если файл больше —
это два файла.

Почему часть папок вне `src`:

| Папка | Что это | Почему не код |
|---|---|---|
| `data/` | темы знаний (`knowledge/*.yaml`), словари, профили компаний (`company-profiles.yaml`), сиды | данные, правятся без сборки |
| `reports/` | шаблон отчёта и промпт интерпретации (`.yaml`, `.md`) | контент, меняется без компиляции |
| `scripts/` | разовые утилиты (`fetch-mcp-ca`, `clean-temp`, пробы) | не входит в рантайм |
| `test/` | unit/e2e и фикстуры | проверки, не продукт |
| `docs/`, `openspec/` | документация и артефакты процесса | не исполняются |


Правила раскладки:

- **Промпт живёт рядом с тем, кто его использует** (`nodes/<node>/prompt.ts`), а не в общей
  папке `prompts/`: при правке узла видно его инструкции.
- **Тул не содержит логики:** схема аргументов, описание для модели и вызов сервиса.
- **Узел не содержит логики:** достаёт данные из состояния, зовёт сервис, кладёт результат.
- **Сервис не знает про MCP, HTTP и граф** — поэтому его используют и тул, и узел, и тест.
- **Репозиторий — единственное место с диском/сетью** для своей области; кэш живёт там.
- **`index.ts` модуля** экспортирует только публичный API: сервис, контракт, типы.
- **Общие помощники** — в файл рядом (`deps.ts`, `instruments.ts`), а не в «утилиты» на весь проект.

## 5. Контракты расширения

Единый способ добавлять функциональность: новый элемент = новый файл + запись в реестре
+ тест. Граф, контроллеры и шаблон при этом не меняются.

| Что добавляем | Контракт | Где регистрируется | Что проверить тестом |
|---|---|---|---|
| Инструмент для модели | `DynamicStructuredTool` (zod-3 схема, описание, `func`) | `McpRegistryService` (тематические) или MCP-сервер (внешние) | вызов с валидными/пустыми аргументами, таймаут, ошибка |
| MCP-сервер | `McpServerConfig` (url, transport, token, allowlist, TLS) | `MCP_SERVERS` + env сервера | discovery, allowlist, статус `up/down`, недоступный сервер не ломает старт |
| Источник новостей | `NewsSourceAdapter` (`id`, `topics`, `fetchNews`, `supportsTickerQuery`, `supportsMatcherQuery`) | `buildNewsRegistry` (фабрика по `SOURCES`) | фильтр по периоду/тикеру, деградация, coverage |
| Источник ставки | `KeyRateSource` | `buildKeyRateSource` | кэш → SOAP → сид → HTML, режим `off` |
| Провайдер фактов отчёта | `FactProvider` (`id`, `section(ctx) → markdown/structured/brief/missing`) | `createProviderMap` + `provider` в шаблоне | при отсутствии данных — `missing`, а не пустая секция |
| Раздел отчёта | `sections[]` в `reports/portfolio-review.yaml` | шаблон (данные) | `missingProviders` пуст, `interpret` ведёт себя как ожидается |
| Узел графа | фабрика `(deps) => async (state) => Partial<state>` | `build-graph.ts` + `routers.ts` | узел отдельно: вход/выход состояния, без сети |
| Интент | `INTENTS` + правило классификатора + маршрут | `state.ts`, `classifier.prompt.ts`, `routers.ts` | правило: положительный и отрицательный примеры |
| Тема знаний | файл `data/knowledge/NN-*.yaml` (`id`, `title`, `summary`, `points`, `details`, `pitfalls`, теги) | каталог читается загрузчиком | тема загружается, отбор находит её по разделу/сектору/вопросу |

Правила контрактов:

- **Контракт — интерфейс, а не класс.** Класс допустим как реализация, но зависимости
  типизируются интерфейсом (так `sources` тестируются без сети).
- **Реестр — единственная точка wiring.** Если элемент не зарегистрирован, он не
  существует: ошибка конфигурации должна быть видна на старте, а не в рантайме.
- **Никакой логики в регистрации.** Реестр хранит и валидирует, но не «додумывает»
  поведение элемента.

## 6. Слой MCP

MCP — это транспорт и каталог, а не место для бизнес-логики. Правила:

1. **Неймспейсинг имён.** Модель видит `<server>__<tool>`; адаптер отдаёт короткие
   имена, реестр добавляет префикс сам (`namespaceTool`). Один инструмент — одно имя,
   без дублей между серверами.
2. **Allowlist по умолчанию.** Разрешено только перечисленное; торговые инструменты
   запрещены всегда (`isForbiddenTool`). Разница между каталогом и allowlist — сигнал
   (`missingTools`, `unlistedTools`), а не тишина.
3. **Схема аргументов — данные сервера.** JSON Schema из MCP конвертируется в zod-3
   (`toZodV3`), потому что провайдеры моделей понимают только zod-3. Валидация входа
   остаётся на стороне MCP: адаптер не «дочиняет» аргументы.
4. **Изоляция отказов.** Таймаут на вызов (`MCP_TOOL_TIMEOUT_MS`), бюджет прогона
   (`ToolBudget`: число вызовов и дедлайн), маппинг ошибок в доменные коды, событие
   вызова для трейсинга. Отказ одного сервера не ломает остальные.
5. **Ленивая инициализация и явное состояние.** Discovery при первом обращении,
   статусы серверов доступны health-проверке; автоповтор discovery — по явному вызову.
6. **Секреты не логируются.** Токен уходит в заголовок или прокси, но не в текст ошибки;
   редактирование — в `platform/observability/redact.ts`.
7. **Версионирование.** Смена схемы инструмента — событие совместимости: allowlist и
   промпты могут отстать. Обновление каталога проверяется тестом и логом о пропавших
   инструментах.

## 7. Инструменты для модели

- **Тонкий инструмент, толстая доменная функция.** Инструмент описывает, что и зачем,
  и вызывает функцию из `report`/`sources`/`collection`. Логика не живёт в замыкании
  инструмента.
- **Описание — для модели, а не для разработчика:** что делает, когда использовать,
  какие аргументы обязательны, в каких единицах результат.
- **Один инструмент — одна задача.** Композитные («всё про бумагу») допустимы, когда
  сокращают число шагов модели, но внутри — те же доменные функции.
- **Идемпотентность и побочные эффекты.** Чтение — свободно повторяется; запись/торговля
  запрещены; если появляется действие, оно идёт через подтверждение и аудит.
- **Ограниченный объём результата.** Инструмент возвращает выжимку, а не сырой JSON:
  ответ модели тоже имеет бюджет (контекст).
- **Локальные тематические инструменты** (`market__*`, `portfolio__*`) собираются из
  источников через `SourceRegistry` и не знают про MCP-детали.


## 8. База знаний

- **Данные, а не код.** Темы живут в `data/knowledge/NN-*.yaml`. Формат задан схемой
  (`KnowledgeBaseSchema`), а не договорённостью. Новый файл — новая тема.
- **Два представления одного знания.** Компактное (`points`) идёт в промпт с жёстким
  бюджетом; полное (`details`, `pitfalls`) — в справочный ответ. Это защищает факты
  брифинга от вытеснения.
- **Отбор, а не поиск.** Статический каталог отбирается по тегам (раздел, сектор,
  вопрос) с весами; векторный поиск вводится только при росте каталога и наличии
  метрик качества.
- **Знания не подменяют данные.** Преамбула и промпты фиксируют: числа — из брифинга,
  выводы на принципах — с пометкой «(оценка)». Исторические примеры не переносятся
  в текущий вывод как факты.
- **Деградация пофайловая.** Битый файл пропускается с предупреждением, остальные темы
  работают; отсутствие каталога — работа без знаний.
- **Качество проверяется тестами.** Тест читает реальный каталог: обязательные темы,
  минимальный объём, теги. Дальше — evals: набор вопросов «что такое X» и проверка,
  что ответ ссылается на нужную тему и источник.

## 9. Граф и узлы

- **Состояние — контракт.** `AgentState` описан zod-схемой: новое поле появляется
  вместе с типом, значением по умолчанию и тестом. Поля-флаги (`partial`, `intent`,
  `scope`) — часть публичного контракта, а не внутренняя деталь.
- **Узел делает одно.** Классификация, ответ, подтверждение, сборка плана, сбор,
  отчёт, справка, знания, новости — отдельные узлы. Если узел начинается с «и ещё»,
  это два узла.
- **Фабрика + зависимости параметром.** `createXNode(deps)` вместо глобального
  состояния: узел тестируется с фейковыми моделью/реестром/конфигом, без сети.
- **Роутеры — чистые функции.** Решение о маршруте зависит только от состояния и
  флагов; побочных эффектов нет, поэтому маршруты тестируются таблицей.
- **Подграфы для веток.** Ветки (`review`, `news`, `help`, `knowledge`) — кандидаты на
  `StateGraph`-подграфы: родитель только маршрутизирует, детали не протекают в общий  граф. Это уменьшает число флагов в `build-graph.ts`.
- **Человек в цикле — `interrupt`.** Подтверждение чтения данных реализуется
  прерыванием с чекпоинтером, а не «ожиданием в памяти»: состояние переживает рестарт.
- **Лимиты и таймауты на каждом уровне:** шаги графа (`recursionLimit`), время модели,
  время инструмента, бюджет прогона, дедлайн.
- **Тестируемость:** e2e на реальном графе с фейковой моделью и MCP-каталогом;
  unit — узлы и роутеры отдельно; фикстуры — общие (`test/fixtures`).

## 10. Переиспользование и поддержка

- **Реестры вместо ветвлений.** Новая возможность = запись в реестре, а не `if` в графе:
  `createProviderMap`, `SourceRegistry`, `INTENTS`, каталог знаний.
- **Один composition root на окружение.** Продовый граф собирает Nest (DI), Studio —
  `agent-runtime`. Обе сборки обязаны использовать один и тот же конструктор графа и
  один список флагов; расхождение ловится тестом «набор флагов совпадает».
- **Фичефлаги — часть конфигурации.** Каждая новая ветка выключаема (`NEWS_FEED_ENABLED`,
  `AGENT_HELP_ENABLED`, `KNOWLEDGE_ENABLED`) и при выключении возвращает прежний маршрут.
- **Версионирование данных.** Шаблон отчёта и база знаний имеют версию; изменение
  формата — новая версия схемы, а не тихое переименование поля.
- **Документация рядом с контрактом:** `docs/reports.md` (шаблон), `docs/sources.md`
  (источники), `docs/knowledge.md` (темы), `docs/mcp.md` (MCP), этот файл (границы).
- **Тестовая пирамида:** много unit на чистые функции, e2e на сценарии пользователя,
  отдельно — тесты деградации (нет данных, нет источника, нет файла).
- **Ревью по чек-листу** (ниже) — дешевле, чем разбираться с протечками слоёв позже.

## 10.1. Маршрутизация и планирование

Маршрут вопроса больше не живёт в узле: `agent/routing` решает его в четыре шага
и фиксирует источник решения (`routeSource`) в состоянии, логе и журнале:

1. `guard` — пустой вопрос, просьба о сделке и посторонняя тема отсекаются
   детерминированно (`routing/guard.ts`); ответ guard попадает в `guardAnswer`.
2. Правила — справка, знания, разбор портфеля, решение по бумаге, новости.
3. Модель — если правила не сработали (строгий разбор одного слова).
4. Безопасный вариант — `data_lookup`, если модель недоступна.

Сбор данных описывается каталогом возможностей (`agent/planning/capabilities.ts`):
восемь доменных фасадов с описанием «когда звать». Планировщик
(`agent/planning/planner.ts`) принимает план модели только по строгой схеме,
повторяет попытку один раз и при неудаче переходит на детерминированный план
сценария (`fallbackPlanFor`). Причина фолбэка сохраняется — по ней считается
метрика `fallbackRate`.

## 11. Антипаттерны

| Антипаттерн | Почему плохо | Чем заменить |
|---|---|---|
| `process.env` вне `config` | конфиг расползается, тесты зависят от окружения | параметр/провайдер `AppConfigService` |
| `readFileSync` внутри узла/движка | скрытая зависимость, медленный классификатор | репозиторий с кэшем, инъекция |
| `new Service()` в бизнес-коде | нельзя подменить в тесте, дублируется wiring | DI-токен |
| Флаги-параметры вместо подграфов | `build-graph` превращается в матрицу случаев | подграф ветки + объект флагов |
| Логика в провайдере MCP/адаптере | домен начинает зависеть от транспорта | тонкий адаптер + доменная функция |
| Ответ модели как источник данных | числа «плывут», отчёт непроверяем | числа считает код, модель комментирует |
| Секреты в логах/ошибках | утечка токена | redact + доменные ошибки без секретов |
| Молчаливая деградация | пользователь не знает, что данных нет | `missing`, `coverage`, лог с причиной |
| Один «универсальный» инструмент | модель не понимает, когда его звать | узкие инструменты с ясным описанием |
| Всё в одном файле (400+ строк) | правки задевают несвязанное, ревью нечитаемо | файл на узел/тул/правило, общие части рядом |
| Промпт в общей папке далеко от ноды | правка узла не видит его инструкции | `nodes/<node>/prompt.ts` рядом с фабрикой |
| Бизнес-логика в туле или контроллере | нельзя переиспользовать и тестировать отдельно | `@Injectable` сервис + тонкая обёртка |
| Тесты только e2e | медленно, непонятно, что сломалось | unit на узлы/чистые функции |

## 12. Чек-лист ревью

- [ ] зависимость идёт по разрешённому направлению, цикла нет;
- [ ] `process.env` не появился вне `src/platform/config`;
- [ ] I/O вынесен в адаптер/репозиторий, бизнес-функция осталась чистой;
- [ ] новая сущность зарегистрирована в реестре и видна на старте (ошибка конфигурации — fail-fast);
- [ ] схема аргументов/состояния/данных описана и провалидирована;
- [ ] ошибка имеет доменный тип, причина не теряется, секретов в тексте нет;
- [ ] есть таймаут/лимит и поведение при отказе (деградация, а не падение);
- [ ] фичафлаг (если ветка) и откат описаны;
- [ ] тесты: unit на новую логику, e2e/интеграция на сценарий, тест деградации;
- [ ] файл остался маленьким; новый узел/тул живёт в своей папке, промпт — рядом с нодой;
- [ ] документация и `.env.example` обновлены вместе с кодом.
