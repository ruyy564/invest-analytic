# Оценка качества агента и инструментов (evals)

Ориентир — практика из статьи Anthropic «Demystifying evals for AI agents»:
eval — это задача с входом и грейдером; попыток (trials) делают несколько, потому
что ответы модели нестабильны; грейдер проверяет **итоговое состояние ответа**, а не
путь к нему; грейдеров несколько и лучше кодовые, чем один «судья»; транскрипты
читают глазами, а сбои из эксплуатации становятся кейсами.

## Пять корзин

| Корзина | Что проверяет | Где | Когда |
|---|---|---|---|
| Контракты инструментов | имя, описание, схема, ответ без данных | `test/unit/tool-contracts.spec.ts` | каждый `npm test` |
| Маршруты | сценарий и область вопроса | `test/eval/cases/dialogues.json`, `test/unit/*intent*` | каждый `npm test` |
| Поведение графа | итоговый ответ на сценарий: тема, причинность, разбор | `test/e2e/agent-baskets.e2e-spec.ts` | `npm run test:e2e` |
| Аналитика | разделы, цитаты с датой и источником, числа | `test/eval/cases/analytics.json` | `npm run eval` |
| Регрессии | подтверждённые сбои прошлых версий | `test/eval/cases/regressions.json` | `npm run eval` |

Правило: **каждый дефект, найденный в эксплуатации, становится кейсом** с тегом
`required`. Правка не считается готовой, пока кейс не проходит.

## Формат кейса

```json
{
  "id": "analytics-cause-lkoh",
  "question": "почему вырос лукойл?",
  "resolvedBy": "rule",
  "intent": "security_analysis",
  "scope": "instrument",
  "target": "LKOH",
  "expectedTools": ["market__factors", "news__search"],
  "forbiddenTools": ["portfolio__snapshot"],
  "trials": 3,
  "tags": ["required", "analytics", "cause"],
  "answer": {
    "mustContain": ["Рыночные факторы"],
    "mustNotContain": ["успешная", "YNDX"],
    "sections": ["Разбор бумаги SBER"],
    "minCitations": 2,
    "minNumbers": 4
  }
}
```

| Поле | Смысл |
|---|---|
| `expectedTools` / `forbiddenTools` | выбор инструментов (tool-choice) — что модель обязана и не вправе вызвать |
| `trials` | число попыток: `pass@k` (успех хотя бы раз) и `pass^k` (все попытки успешны) |
| `tags` | группы отчёта: `required`, `analytics`, `cause`, `news`, `regression` |
| `answer.sections` | обязательные разделы ответа (заголовки): структура аналитики |
| `answer.minCitations` | минимум строк «• 2026-11-05 [интерфакс] …» — причина без источника не принимается |
| `answer.minNumbers` | минимум чисел: «выросла» без цифр — не аналитика |

## Грейдеры

Кодовые (без сети, детерминированные):

- `contains:<фрагмент>` / `notContains:<фрагмент>` — обязательное и запрещённое;
- `section:<заголовок>` — раздел есть (структура отчёта);
- `citations:>=N` — строки-цитаты с датой и источником;
- `numbers:>=N` — числа в ответе;
- `no-refusal` — нет отказа модели;
- `tool:<имя>` / `forbiddenTool:<имя>` — вызванные инструменты.

Судья по рубрике (`scripts/eval-judge.mjs`, `src/eval/judge.ts`) — дополнительный
слой: модель ставит 1–5 по осям и возвращает `{score, reason}`. Судью калибруют на
20–30 кейсах против человека, иначе оценки «плывут». Кодовые грейдеры важнее: они
не зависят от модели.

## Как прогонять

```bash
npm test                                   # контракты, маршруты, юниты
npm run test:e2e                           # корзины поведения на фейковом MCP
npm run eval                               # все корзины кейсов (offline)
npm run eval -- --cases test/eval/cases/analytics.json   # одна корзина
npm run eval:live                          # живая оценка: 5 прогонов на кейс
npm run eval -- --mode live --runs 5       # то же через `eval --mode live`
npm run eval -- --mode judge               # судья по рубрике (нужен LLM_API_KEY)
```

Offline-режим берёт **записанные** ответы (`test/eval/transcripts/<id>.txt`);
кейсы без записи перечисляются как пропущенные и не считаются провалом.
Ненулевой код возврата — есть проваленные кейсы.

Offline повторяет один и тот же записанный ответ, поэтому `pass@k` и `pass^k` там
всегда равны — это проверка **контракта** ответа, а не стабильности модели.
Разброс видно только в живом режиме.

## Живые прогоны: «3 из 5»

`npm run eval:live` гоняет каждый кейс через работающий сервис (LLM + MCP) N раз
(`--runs`, по умолчанию `trials` кейса или 5) и оценивает **каждый** ответ теми же
грейдерами. Метрика по кейсу — доля успешных прогонов:

```
  ok  analytics-brief-sber #1 — 13 с
  bad analytics-cause-lkoh #2 — citations:>=2 — цитат 1, нужно 2
  ✔ analytics-brief-sber: 3/3
  ✕ analytics-cause-lkoh: 2/3
Кейсов: 2, прогонов: 6, ниже порога 60%: 1
```

- `--min-pass-rate` (по умолчанию `0.6`) — порог: «3 из 5» проходит, «2 из 5» нет.
  Для регрессий с тегом `required` разумно ставить `--min-pass-rate 1` и требовать
  стабильности, для исследовательской аналитики хватает 0.6–0.8.
- `--force` не нужен: живые прогоны ничего не записывают. Чтобы обновить эталоны,
  используйте `npm run record:transcripts -- --force`.
- Ненулевой код возврата — есть кейсы ниже порога.

## Что делать при сбое

1. Прочитать транскрипт (`npm run trace`, LangSmith или `test/eval/transcripts`).
2. Понять, что сломалось: маршрут, инструмент, грейдинг ответа или сам ответ.
3. Добавить кейс в подходящую корзину с тегом `required` (вопрос — дословно из
   эксплуатации).
4. Починить и убедиться, что кейс проходит; затем прогнать все три команды.

## Как добавить кейс

1. Скопируйте шаблон `test/eval/cases/regression-template.json`.
2. Заполните `id`, `question`, маршрут, `tags`, грейдеры.
3. Положите записанный ответ в `test/eval/transcripts/<id>.txt` (для offline и judge).
   Ответ разбора бумаги записывает `node scripts/record-brief-transcript.mjs`: он
   собирает отчёт из реального кода на фикстурах и кладёт транскрипт
   `test/eval/transcripts/analytics-brief-sber.txt` — без сочинения текста руками.
4. Прогоните `npm run eval` и убедитесь, что кейс проходит или падает ожидаемо.

### Как записать транскрипты живьём

Ответы, которые пишет модель, руками не придумать — их записывает раннер по
работающему сервису:

```bash
npm run build && npm run start            # сервис на 127.0.0.1:3000
npm run record:transcripts                # все кейсы без транскрипта
npm run record:transcripts -- --only help,market-news --force   # выборочно
```

Скрипт (`scripts/record-transcripts.mjs`) для каждого кейса проходит подтверждения,
поддерживает `history` (предыдущие вопросы той же сессии) и не перезаписывает
существующие файлы без `--force`, чтобы детерминированные транскрипты не затирались.

Офлайн-транскрипт не содержит вызовов инструментов, поэтому `expectedTools` в
offline-режиме не проверяется (это отсутствие данных, а не провал); выбор
инструментов проверяют e2e-корзины, где прогон записывается целиком.

## Аудит аналитики

Что у нас есть и чего не хватает до формата инвест-дома — в `docs/analytics.md`.
Корзина `analytics.json` — контракт на этот формат: разделы («Что влияет на бумагу»,
«Хорошо, нейтрально, плохо», «Чего ждём»), цитаты с датой и источником, числа.
