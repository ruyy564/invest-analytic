# Правила подтверждений

Перед чтением данных брокера агент останавливается в узле `approve` и ждёт явного решения пользователя. Перечень действий задаётся **одним файлом** — `src/agent/approvals/approval-rules.ts`; код графа и роутеров этот перечень не содержит.

## Формат правила

```ts
{
  tool: 'tinkoff__invest_get_portfolio',   // имя инструмента или шаблон с *
  label: 'Состав и стоимость портфеля',    // короткое название для списка действий
  question: 'Прочитать данные портфеля у брокера?',
  requiresApproval: true,                  // false — явное исключение
}
```

Обязательны `tool`, `label`, `question`. `requiresApproval` по умолчанию `true`.

## Встроенный набор

| Инструмент | Подтверждение | Почему |
|---|---|---|
| `tinkoff__invest_list_accounts` | нет | Служебное чтение: нужно, чтобы показать конкретный счёт в запросе подтверждения. Данных о позициях не раскрывает |
| `tinkoff__invest_get_portfolio` | да | Состав и стоимость портфеля |
| `tinkoff__invest_get_positions` | да | Позиции портфеля |

Так пользователь получает **одно** подтверждение на вопрос о портфеле, а не два.

## Сопоставление

- точное имя: `tinkoff__invest_get_portfolio`;
- шаблон: `tinkoff__invest_*` (подходит и для будущих инструментов сервера);
- применяется **первое** совпавшее правило сверху вниз — порядок в файле значим;
- если правила нет — действует `APPROVAL_UNLISTED` (`require` по умолчанию).

`require` по умолчанию — осознанный fail-safe: новый инструмент из нового MCP-сервера не начнёт тихо читать данные.

## Внешний файл правил

`APPROVALS_FILE=./config/approvals.json` полностью заменяет встроенный набор (удобно менять правила в контейнере без пересборки):

```json
{
  "unlisted": "require",
  "rules": [
    {
      "tool": "tinkoff__invest_get_portfolio",
      "label": "Состав и стоимость портфеля",
      "question": "Прочитать данные портфеля у брокера?",
      "requiresApproval": true
    }
  ]
}
```

Файл валидируется той же zod-схемой; ошибка чтения, парсинга или схемы останавливает старт.

## Проверки при старте

| Проверка | Результат |
|---|---|
| Дубликат `tool` | `ConfigError` |
| Отсутствует `label` или `question` | `ConfigError` |
| `requiresApproval: false` для торгового инструмента (`invest_create_*`, `invest_post_*`, `invest_cancel_*`, `invest_replace_*`, `invest_deposit_*`, `invest_transfer_*`, `invest_sell*`, `invest_buy*`) | `ConfigError` |
| Правило ссылается на инструмент, которого нет в каталоге MCP | `ConfigError` при проверке каталога (`assertKnownTools`) — discovery ленивый, поэтому проверка выполняется при первом обращении к реестру |

## Строгий режим

Согласие **не переносится** на следующий вопрос: ни в той же сессии, ни в другой сессии,
ни в глобальное хранилище. Новый вопрос, требующий чтения, снова останавливается на `approve`.

Внутри одного прогона согласие действует до конца: если модель после первого чтения
решает запросить ещё один инструмент (например, сначала цену, затем карточку бумаги),
второго подтверждения не будет. Признак живёт в состоянии прогона (`dataApproved`),
сбрасывается в узле `classify` при новом вопросе и не сохраняется между прогонами.

## Как подтверждать

- **HTTP-API**: `POST /api/v1/agent/chat/approve` с `{ "sessionId": "...", "approved": true }`.
  Поле `approved` обязательно, поэтому пустого решения здесь не бывает: `false` — отказ.
- **LangSmith Studio**: панель `Interrupts` → поле значения и кнопка `Resume`.
  Введите `true` (или `{"approved": true}`) и нажмите `Resume` — прогон продолжается
  и строит отчёт. **Пустое поле не сработает**: Studio отправляет `""`, и
  LangGraph-сервер отвечает `EmptyInputError: Received empty Command input`
  (ошибка до узла `approve`, поэтому данных не читает никто).
- **Отказ в Studio**: `{"approved": false}` (или `false`, `"нет"`) — ни одного
  чтения не выполняется, ответ объясняет, что данные не запрашивались.
- Узел `approve` понимает решение в любом из видов: `true`/`false`, `"да"`/`"нет"`,
  строка JSON, `{ "approved": true|false }`, `{ "decision": "decline" }`.
  Неизвестный текст считается отказом — данные не читаются.

## Что подтверждения не требует

- **Справка о возможностях** (ветка `help`): не читает данные и не вызывает инструменты — подтверждение не запрашивается.
- **Сводка новостей рынка** (ветка `news`): читает только публичные источники, не данные счёта.
- **Динамика цены бумаги** (`market__price_dynamics`): публичные котировки за период — состав портфеля и суммы инструмент не читает, поэтому вопрос «что с бумагой» получает числа без лишнего шага подтверждения.

Ожидание ограничено `APPROVAL_TTL_MINUTES` (по умолчанию 15): подтверждение, пришедшее позже, отклоняется с `APPROVAL_EXPIRED` (`410`). Удаление брошенных сессий делает очистка по `STATE_TTL_DAYS`.

## Как добавить подтверждаемое действие

1. Добавьте правило в `approval-rules.ts` (или в `APPROVALS_FILE`). Имена — уже с префиксом сервера: `news__get_article`.
2. Если инструмент разрешён в `MCP_<NAME>_ALLOWED_TOOLS`, но правила нет — подтверждение всё равно потребуется (`APPROVAL_UNLISTED=require`).
3. Граф, узлы и роутеры не меняются.

## Структурные признаки ответов

Отказ пользователя и прерванный вызов помечаются в `ToolMessage` полем
`additional_kwargs.kind` (`denied` / `interrupted`). Это не текст и не эвристика:
узел ответа пропускает такие сообщения и не принимает их за готовый отчёт.

Готовый отчёт узла разбора передаётся полем состояния `lastResult` с видом
`report`; текст модели — видом `analysis`. Поэтому смена формулировки отчёта не
ломает поведение.

## Что видит пользователь в запросе

Payload подтверждения содержит не только действия, но и границы согласия:
`limits` (`maxCalls`, `deadlineMs`, `approvalTtlMinutes`) и `expiresAt`. Поэтому
пользователь заранее знает, сколько вызовов разрешает и когда согласие истечёт.

Правила по умолчанию: любое чтение данных брокера (включая фасады `instruments__*`)
требует подтверждения; публичные новости (`news__search`) — нет.
