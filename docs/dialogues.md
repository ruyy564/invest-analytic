# Корзина диалогов и эталонные ответы

Корзина фиксирует, **как сервис должен отвечать на типовые вопросы**, чтобы не проверять
всё вручную после каждой правки. Один файл — один список кейсов:

```
test/fixtures/dialogues.json      вопросы, ожидаемый маршрут и фрагменты ответа
test/unit/dialogues.spec.ts       проверка маршрута и эталонного ответа
test/e2e/agent-graph.e2e-spec.ts  полный прогон графа для ключевых сценариев
```

## Формат кейса

```json
{
  "id": "buy-plzl",
  "question": "стоит ли покупать полюс золото",
  "resolvedBy": "rule",
  "intent": "portfolio_review",
  "scope": "instrument",
  "target": "PLZL",
  "answer": {
    "mustContain": ["Разбор бумаги PLZL", "• цена за 1 шт.:", "Справочный контекст"],
    "mustNotContain": ["Динамика PLZL за", "Состав портфеля", "% портфеля"]
  }
}
```

| Поле | Смысл |
|---|---|
| `resolvedBy` | `rule` — маршрут решает детерминированное правило; `llm` — метку выбирает модель, проверяем только область |
| `intent` | ожидаемая ветка: `data_lookup`, `security_analysis`, `portfolio_review`, `market_news`, `agent_help`, `knowledge_question`, `off_topic` |
| `scope` / `target` | ожидаемая область разбора и тикер |
| `answer.mustContain` | фрагменты эталонного ответа (отчёт собирается кодом; для разделов модели проверяется заголовок и брифинг) |
| `answer.mustNotContain` | чего в ответе быть не должно (например, одиночной динамики цены) |

Кейсы без `answer` проверяют только маршрут: текст такого ответа пишет модель, и
фиксировать его в тесте нет смысла.

## Ключевое правило: решение по бумаге — это разбор

«Стоит ли покупать X», «продавать или держать X», «перспективы акций X» — это не
точечный вопрос по данным. Такие вопросы уходят в `portfolio_review` с областью
`instrument`: сервис собирает цену, динамику, график, прогноз, дивиденды, профиль и
новости бумаги, показывает справочный блок и даёт сбалансированную оценку с
напоминанием, что это не индивидуальная инвестиционная рекомендация.

Свободный агент (`security_analysis`) в таком случае отвечал одной динамикой цены —
поэтому для вопросов-решений добавлено правило `DECISION_PATTERN` (в
`src/agent/nodes/classify/prompt.ts`), а в промпт агента — требование собирать
несколько источников и помечать суждения как оценку.

## Бумага из предыдущего вопроса

Если бумага названа в предыдущем вопросе, а следующий ссылается на неё местоимением
(«расскажи о Сбере» → «стоит ли её покупать»), область разбора наследуется: правило
`DECISION_PATTERN` видит действие, а маршрутизация берёт тикер из предыдущего вопроса
(`previousQuestion` в `routeQuestion`). Без названной ранее бумаги тикер не угадывается —
вопрос остаётся портфельным.

## Уточнение: «расскажи детальней»

Уточняющий вопрос («расскажи детальней», «подробнее», «а почему», «что ещё») своей темы
не имеет, поэтому маршрутизация наследует её у предыдущего вопроса: `isFollowUpQuestion`
плюс `previousIntent` дают тот же сценарий и область, и граф помечает прогон `followUp`.
Далее узел агента берёт **прошлый прогон** (`previousRun`) — его ответ и результаты
инструментов, — и передаёт модели сам предыдущий ответ с просьбой развернуть детали.
Без этого «расскажи детальней» уходило в «это вне моей компетенции», а модель отвечала
пустым текстом.

## «Что с бумагой?» и короткие вопросы

«Что со сбером», «что с самолётом» — тоже вопросы о движении: `asksWhatWith` срабатывает,
когда бумага названа, а спрашивают не цену («что с ценой Сбера» — обычный путь данных).
Если бумага распознана по алиасам, маршрутизатор не ставит `off_topic`, даже когда
классификатор ошибся на коротком вопросе.

Динамику цены узел запрашивает сам (`market__price_dynamics`, 180 дней): модель может
промолчать и не вызвать инструмент, а тогда ответ «что с бумагой» остаётся без чисел.
Котировки публичны, поэтому подтверждение для них не нужно. Период в вопросе
(«за последние пол года») на глубину не влияет: показывается полугодовое окно.

## Эксперт, а не справочное бюро

Агент отвечает не заготовкой из файла, а разбором: база знаний подаётся в системный
промпт **под вопрос** (`promptBlock({ question })`, до четырёх тем), инструменты дают
данные, а вывод формулирует модель.

- **Деньги вне бумаг.** «Стоит ли покупать квартиру в ипотеку», «гараж или вклад»,
  «что выгоднее — ИПС или депозит» — это `data_lookup`, а не `off_topic`: агент получает
  темы про налоги, риски и чек-лист решений, отвечает по критериям и задаёт 1–2
  уточняющих вопроса (доход, взнос, срок), если без них вывод невозможен.
- **Незнакомая бумага.** «Что за бумага Хэдхантер» — это `security_analysis`:
  вопрос про бумагу распознаётся правилом, а тикер находит инструмент
  (`invest_find_instrument`). Список алиасов ускоряет распознавание, но не ограничивает
  круг бумаг: отказ «вне компетенции» на новую бумагу — ошибка.
- **Понятия.** «Что такое P/E» попадает в ветку `knowledge`, где отвечает модель-эксперт
  по теме из базы знаний; выжимка из файла остаётся запасным вариантом.

## Ответ строится на данных текущего прогона

Результаты инструментов прошлых вопросов в треде не переиспользуются: готовый отчёт
прошлого прогона (сводка по счетам, динамика цены) не подменяет ответ на новый вопрос,
даже если он лежит в истории сообщений. Правило живёт в `currentRun`
(`src/agent/nodes/agent/agent.node.ts`).

Готовый отчёт кода отдаётся сразу только для точечного вопроса по данным. На «стоит ли
покупать» и «почему упал» данные передаются модели для трактовки, а отчёт остаётся
резервом ответа, если модель промолчала или повторно просит уже полученный инструмент.

## Вопрос о причине движения цены

«Почему упал/вырос X», «что случилось с Яндексом» — единственный случай, когда ответ
нельзя собрать из данных брокера: там только цены и объёмы. Поэтому:

1. узел агента сам запрашивает `news__search` по каждой названной бумаге (публичный
   источник, подтверждение не нужно) — окно 90 дней и до 12 публикаций: движение цены
   за полгода объясняют и более ранние новости. Фасад ищет не только по тикеру, но и по
   алиасам эмитента (`LKOH`, «Лукойл», «ЛУКОЙЛ»), новости брокера запрашиваются по
   `TICKER_CLASSCODE` (`LKOH_TQBR`) — по одному тикеру брокер их не находит. Если по
   бумаге публикаций нет, запрашивается общая повестка: причины часто отраслевые —
   нефть, курс валюты, ставка ЦБ, санкции. `detectInstruments` находит все бумаги
   вопроса, включая разговорные короткие формы («вк» → VKCO), а не только первую;
2. у каждой публикации в ответе инструмента есть **аннотация** (первые ~240 символов
   содержания), а первые статьи дочитываются **целиком** (`fullText: true`, до 1 200
   символов текста): разметка чистится в `stripMarkup`, поэтому модель видит факты, а
   не HTML и не один заголовок; по тексту она и называет 2–3 конкретных фактора;
3. поиск идёт не только по бумаге, но и по **факторам**: `news__search` с `factors: true`
   добавляет блок «Факторы» — публикации по драйверам сектора бумаги (из
   `data/company-profiles.yaml`: нефть/Brent для нефтегаза, металлы, ставка для банков)
   и по общим рыночным факторам (курс рубля, ключевая ставка, санкции). Так в ответ
   попадают причины, в которых бумага не названа: «выборы в США обвалили цены на нефть»;
4. числа по рынку даёт `market__factors`: нефть Brent (индекс `RUCBRNCP`), доллар и юань
   к рублю, ключевая ставка ЦБ — значение и изменение за период. На вопрос о причине узел
   агента запрашивает их сам: «Brent −4 % за месяц» — аргумент, «возможно, нефть выросла» —
   догадка;
5. новых источников можно добавить **данными** — записью в `data/news-sources.yaml`
   (`NEWS_EXTRA_FEEDS_FILE`): ЦБ, отраслевые ленты, ИР-страницы компаний;
2. ответ модели принимается, только если он ссылается на найденную публикацию или прямо
   говорит «Причина не установлена». Тикеры в ответе должны быть из данных прогона —
   «YNDX» вместо «YDEX» считается вымыслом;
3. иначе отдаётся ответ по фактам: движения цен из прогона, публикации с датой и
   источником и честная фраза о том, что причина не установлена.

Правила живут в `src/agent/nodes/agent/cause.ts`, проверяются `npm test -- cause-answer`.

## Как прогнать

```bash
npm test -- dialogues      # маршруты и эталонные ответы (15 кейсов)
npm run test:e2e           # полный прогон графа, включая «стоит ли покупать Сбер»
```

## Как добавить кейс

1. Добавьте запись в `test/fixtures/dialogues.json`.
2. Если `resolvedBy: "rule"` — убедитесь, что правило действительно срабатывает
   (иначе тест покажет расхождение).
3. Если нужен эталонный ответ — заполните `mustContain`/`mustNotContain` тем, что
   должно быть в markdown-отчёте.
4. Прогоните `npm test -- dialogues`: расхождения печатаются по id кейса.
